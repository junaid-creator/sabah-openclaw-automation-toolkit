# Authorized recovery snapshot and independent alert

Read only when a separate owner request authorizes a backup, restore rehearsal, or outage-alert implementation after the audit. It does not authorize production restore, Gateway restart, public publication, missed-job replay, or a recurring backup schedule.

1. **Scope first.** Inspect live Gateway service/drop-ins, user and system timers, integrity watcher and its stop policy, service account/lingering, current named channels, backup locations and free space. Inventory configuration, credentials, agent/session state, application workspaces and business ledgers. Keep bulk caches, historical backups and remote SaaS state distinct from critical recovery inputs. Do not print credential contents or change protected plugin/guard files merely to install monitoring.
2. **Snapshot without stopping production.** Choose a private destination outside live state; record date, source paths, source/backup modes and SHA-256 hashes. Use SQLite's online backup API for active databases, including WAL-backed ledgers, instead of a plain file copy. Preserve originals and record inaccessible paths individually; do not silently call the backup complete. Copy live non-SQLite files as point-in-time data and disclose that cross-file transaction consistency is unproven. A backup on the production filesystem is interim local recovery, not off-server disaster protection.
3. **Prove what can be restored.** Restore the captured paths into an isolated empty directory, compare hashes after copying and run SQLite integrity checks on each database. Check critical configuration, agent state, business ledger and unit files explicitly. Document a safe recovery order and remote-state reconciliation before enabling any publisher. A copy-and-integrity check is not an isolated Gateway boot or an off-host restore; name each remaining gate.
4. **Independent alert branch.** Only when authorized, use a separate service/timer/state directory whose probe and notification do not depend on the Gateway process being healthy. Inspect existing monitor/watcher units first and merge without altering their ExecStart or stop policy. Require repeated failed readiness probes after startup grace; suppress planned maintenance and evidenced integrity stops. Persist an incident and notification attempt before transport handoff, keep a confirmed message ID distinct from unknown delivery, and do not blindly retry an uncertain send. A recovery notice requires a previously confirmed outage alert. Keep the monitor alert-only unless restart behavior is separately requested and designed. Use only a permitted outbound transport and verified owner destination; a connected channel alone is not receipt evidence.
5. **Test boundaries separately.** Simulate startup grace, sustained failure, deduplication, recovery and maintenance/integrity suppression in disposable state without stopping the real Gateway. If a live owner-only TEST is explicitly authorized, send one labeled notice and retain the actual transport receipt; an API/tool receipt does not prove handset display. Verify unit syntax, enablement, natural timer invocation and persisted healthy state; then recheck Gateway health/readiness, named channels and existing watcher/SEO/watchdog timers. Document a monitor-only rollback that preserves incident receipts. Report backup scope, excluded files, restore-copy proof, remote/off-server gaps, live test receipt and production state separately.
