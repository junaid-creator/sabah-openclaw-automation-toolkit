# WooCommerce cart and checkout diagnosis

Use for non-paying product → cart → checkout acceptance, or when Store API/cart counters disagree with rendered cart, a block stays loading, or an enabled gateway is absent at checkout. This is not a price correction or product-copy audit. For catalog and variation identities use [catalog reconciliation](../woocommerce-catalog-reconciliation/SKILL.md); for source-versus-discount semantics use [price display audit](../woocommerce-price-display-audit/SKILL.md). Diagnosis alone does not authorize changing optimization, checkout or payment configuration.

1. For customer acceptance, use a fresh isolated guest context (and a mobile viewport in its own fresh context when requested). Establish an empty cart; select a valid product/variation and wait for the hidden variation ID and displayed effective price to settle before clicking Add once. Follow that same context through product → cart → checkout, comparing product, variation, quantity, price and total. A click may navigate while the document is still loading; wait for the destination and reconcile any uncertain add from the cart before retrying. A header count, mini-cart or Store API result does not prove the dedicated cart renders. Do not submit checkout or payment. Remove only this context’s test items using the rendered cart control, wait for the empty state and confirm the Store API has zero items; closing the context alone is not cleanup.
2. Wait for the **actual cart line item and totals** within the Cart Block, not merely its shell, heading or matching product text in a mini-cart/recommendations. The shell can appear before hydration; confirm the selected item and final total appear without clicking after the normal load. A transient blank row is not a proven defect, but report a material delay rather than calling it immediate. Check the final rendered block on both viewports and wait for the remove control before cleanup. If the block remains loading or shows empty despite a confirmed cart, inspect assigned page content, rendered DOM, console and script tags/network. In the verified LiteSpeed failure, scripts were emitted as `type="litespeed/javascript"` with `data-src`, no Store API request occurred, and a first click activated rendering. Verify current behavior before attribution; do not confuse this click-dependent failure with ordinary hydration or an add that never landed.
3. For authorized repair, inspect the exact LiteSpeed options before changing them. Prefer its URI Page Optimization exclusion (`litespeed.conf.optm-exc` on the inspected installation) for only the assigned cart/checkout paths, preserving existing entries and the global JS-delay setting. Back up prior values and page content, verify readback and fresh no-click browser renders. A broad cache-disable or product rewrite is not the same narrow repair. Check the actual public response after any purge attempt rather than treating a CLI purge result as page behavior.
4. If checkout renders but reports no payment methods, compare configured enabled gateways with the live checkout UI and inspect the installed gateway's Checkout Block registration. An enabled classic gateway may not register a block payment method. Do not enable a different payment method or claim a working charge. Where compatibility is proven and change is authorized, back up the exact checkout page content and switch only that page to WooCommerce's `[woocommerce_checkout]` shortcode, retaining its page ID and gateway settings. Verify the selected item/variation, total, required fields and intended gateway in the fresh rendered classic form; where the visible gateway label is generic, inspect its payment-method input value (for example `wctelr`) rather than treating absence of the word “Telr” in page text as absence of the gateway. A visible gateway is not a processed payment.
5. After an authorized repair, read back scoped settings/pages and compare protected product/variation data, SEO, prices and images against a pre-change snapshot. For either branch, report cart rendering, quantity/variation totals, checkout form and gateway visibility separately from an untested order/payment. Confirm the test cart is empty and record any unresolved console/server errors by their actual scope.

Completion: same-session rendered cart and checkout evidence for each requested viewport, empty test cart, and explicit payment-processing limit. For an authorized repair, also include before/after evidence, narrow configuration/content delta with backups and protected commerce-record comparison; a read-only acceptance check does not require or authorize those changes.
