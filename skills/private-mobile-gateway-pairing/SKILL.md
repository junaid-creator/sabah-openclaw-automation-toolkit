# Private Gateway mobile pairing

Use when a remote native OpenClaw app needs this existing Gateway over a private tailnet. For client-specific pairing or auth failures after scanning, use the installed node-connect procedure. This skill does not authorize installation, config changes, operator access or device approval without task-specific owner permission.

1. Lock the exact Gateway service, config/profile and ordinary listener. Inspect bind, auth, Tailscale status and `tailscale serve status --json`; a similarly named public website is not the Gateway. Before privileged installation or an operator grant, inspect the actual Unix user, sudo policy and shared administrator session; permissive exec policy is not root. Preserve the laptop SSH tunnel, token, agents, plugins and automations. Use Serve, never Funnel, for tailnet-only access. Owner completes administrator and Tailscale sign-in privately; do not relay credentials or short-lived sign-in URLs through chat.
2. After authorized setup, verify Tailscale is Running and Serve routes HTTPS 443 to a Gateway-owned loopback listener. Verify the ordinary Gateway listener remains loopback-bound and the service stable. If a restart is queued or draining retained work, saved configuration is not activation; reconcile process start time, Serve status and health before another attempt. Check requested accounts with `openclaw channels status --probe`; a restart-loop warning on an unrelated stopped `default` account does not mean a running named account needs restarting. Do not clear or relink credentials to remove it.
3. Require HTTPS 200 with a valid certificate. If the VPS cannot resolve its MagicDNS name after `--accept-dns=false`, obtain its live tailnet IP from `tailscale status --json` and use `curl --resolve <magicdns>:443:<tailnet-ip> https://<magicdns>/`; this preserves TLS SNI and hostname verification without changing DNS. A host-local check does not prove phone DNS, ACL or reachability. Probe WebSocket with `curl --http1.1` plus Upgrade, `Sec-WebSocket-Version: 13` and a valid `Sec-WebSocket-Key`; require `101 Switching Protocols`. Curl over HTTP/2 returning 200 is not a WSS handshake. A later timeout after 101 may just be the socket remaining open, not a failed handshake or proof of authenticated app use.
4. Inspect official QR metadata without exposing payload: `openclaw qr --json | jq '{gatewayUrl,gatewayUrls,auth,access,accessDowngraded,urlSource}'` on the locked local Gateway. For Full Access require the intended `wss://<magicdns>` URL, token auth, `access: "full"` and no downgrade; do not pass `--limited`. Metadata is not proof that a fresh QR was displayed or scanned. Have the owner open **Control UI → Devices → Pair device**, select Full Access and scan its fresh official QR in the mobile app. Keep the QR/setup credential in that private UI or a terminal outside agent tooling, never chat, attachments or tool-visible output. The phone needs Tailscale on the same tailnet on both Wi-Fi and mobile data.
5. After a phone attempt, correlate new pending request ID, client, role, platform, address and retry time. Re-list immediately before approving the exact request ID; `--latest` is preview only. Verify the native mobile node connects to this Gateway and no immediate auth/reconnect failure follows. No phone peer or pending request means pairing unverified, not complete. Report separately Gateway stability, Serve/private listener, host HTTPS/WSS, phone-side reachability, named channels, QR display, approval and connected phone. Preserve unrelated stopped accounts and existing devices.
