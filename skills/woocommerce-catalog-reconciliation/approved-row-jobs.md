# On-demand approved row jobs

Use when generalizing a one-time catalog synchronizer into live row-specific CHECK/ADD/UPDATE/APPROVE jobs. Apply the main skill’s catalog verification and mirror recovery; use [restricted command bridges](restricted-command-bridges.md) for transport authentication, cancellation ordering and subprocess acceptance. This procedure does not establish standing publication, imagery or stock policy.

1. Replace historical fixed-row assumptions with a fresh complete source read and schema validation. A moved row is not a new identity; a move after review invalidates that plan. Check recorded IDs against all-status parent/variation SKUs and approved aliases. Normalize option aliases with explicit collision detection **before** building a dictionary: alias plus canonical spelling must not silently select the last price, even when both prices agree. Reject malformed entries rather than omitting them.
2. Reserve the intended identity, not just the row or existing numeric ID. For a new blank-SKU row, freeze the generated SKU and canonical name/model reservation keys; check duplicate source rows and all active/uncertain jobs across channels. A moved or copied row must not create a competing job while an earlier creation has no returned ID. For a consolidated family, validate both sibling source identities/options and fingerprint retained historical parents as protected non-write dependencies; checking only the canonical parent or mentioning preservation in a warning is insufficient.
3. Show the full actual immutable write plan before approval: generated descriptions, slug, categories/attributes, visibility, stock/status, image behavior, exact changed fields and source/SKU/metadata writeback policy, with its digest. Reject overlength review before creating an approvable job unless a verified attachment-review path exists. Tests must include genuine new simple/variable plans and non-noop updates; no-change CHECKs can miss construction failures. Generated defaults and claims require the current task’s authority; do not generalize a prior draft-only deployment into a permanent rule.
4. Bind approval to the authenticated owner/account, job, exact digest and expiry. Before remote work persist the approval, backup proof and phase intent durably. For creation, bind new parent/children to job/digest ownership markers and persist returned IDs before verification. After unknown outcomes, a matching SKU alone is insufficient: reconcile ownership markers, the complete expected child set, fields and protected dependencies. Never invoke creation again to repair missing metadata or finish an unexplained partial parent.
5. Verify the remote result before generating the intended source mirror. Persist that result, original verification timestamp and exact B/I:N-equivalent values. On mirror-only retry accept only original or exact intended source values, skip already-completed writes and recheck row identity/formulas immediately before each write and after readback. A blank generated-SKU cell must not conceal a formula. Preserve SHEET_PENDING on uncertainty, never recreate the product. Document the residual race with external row sorting/edits; local locks are not cross-service compare-and-set.
6. Test actual Woo setters/verifiers separately from fixture lifecycle tests: a copied WordPress core plus Woo and a fresh socket-only test database can exercise simple/variable creation, duplicate rejection and price/copy updates without production writes. Block external WordPress HTTP/cron, isolate filesystem/configuration, and stop test databases afterward. Exercise backup/export/gzip and restore into another test database. Label this isolated adapter/restore evidence, not a production canary or restored production backup. Accept only narrowly observed derived representations (for example, a no-image empty string versus zero); negative tests must still reject unexpected media, URLs, metadata and protected fields.

Completion: supported versus explicitly blocked plan classes, exact review content, reservation/replay/cancellation and mirror-failure regressions, actual isolated adapter results, separate live read/channel evidence, and an independently authorized production canary if required. A hardcoded refusal of every APPROVE is preview-only implementation, not completed approved execution.
