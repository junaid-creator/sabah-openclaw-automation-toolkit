# Multi-platform publication recovery

## Portable installation boundary

Read [README.md](README.md) before executing this procedure. The authored
reference workflow below describes diagnostic evidence and safety gates.
Reference script names, table names, job prefixes and state paths are schema
examples, NOT commands shipped or activated by installing this skill. Map them
to the configured deployment first. Missing adapters are blockers; do not invent
commands or bypass authorization. This package is a procedural skill, not the
complete underlying engine.


Use when a reviewed job targets multiple platforms, an API returns only a task or post ID, platforms finish differently, or a prior run must be reconciled. This procedure does not authorize publication. When an approved job never reached the durable ledger at all, diagnose the intake stage first with [smgc-publication-intake-diagnosis](../smgc-publication-intake-diagnosis/SKILL.md).

1. Freeze the authorization boundary. Read the durable approval receipt and bind it to the exact job, asset hash, captions, hashtags, and target set. One approval may cover all targets frozen in that receipt, but never changed content, added platforms, or a Sheet row by itself. If its review provenance is missing or synthetic, use [automation-adapter-verification](../automation-adapter-verification/SKILL.md) to distinguish genuine later delivery/approval evidence from an accepted production binding. Preserve the original receipt and remote attempt history; require supported audited reassociation rather than editing old approval JSON or clearing REVIEW_REQUIRED. For an explicitly narrowed target set on a delivered draft with no durable approval or attempts, use [review target reduction](../automation-adapter-verification/review-target-reduction.md); it preserves the original evidence and requires validated revised delivery rather than editing an old binding. An expired schedule is not revived by finding a later preview: any new timing/platform scope needs its own valid authorization.
2. Reconcile before any write. For each `(job_id, platform)`, inspect the durable approval receipt, ledger, operation/task record, platform post log, and current remote state. Treat that pair as the idempotency key. If a task, remote post ID, or confirmed success already exists, inspect its status/link without a new submission; never replace it merely because the link or report is missing. Check the installed recovery eligibility selector against the actual saved receipt before relying on a timer: a running timer can deliberately skip a legacy approval without the new admission marker. Never add that marker to historical receipts. If a scoped existing-task reconciliation command is available, inspect its effects first; its remote calls may be read-only while it still writes ledger, Sheets and notifications. Keep a container merely ready to publish distinct from a published post; do not invoke a publish-capable continuation under read-only authority.
3. Preflight both write and verification capabilities before the first submission. Validate account binding, public-post settings, media compatibility, publish permission, and the read permission needed to retrieve an owned post and canonical share URL. If verification permission is absent, fail closed before posting; do not create a result that the workflow cannot later prove. Identify the installed API family from its base URL and actual publish/read endpoints before recommending authorization changes. For TikTok, a Business Accounts adapter using `business/photo/publish/` and `business/video/list/` is not the developer Content Posting adapter. A local error named `VIDEO_LIST_PERMISSION_REQUIRED` or a checked scope string does not prove the corresponding Business permission/consent mapping. Preserve the existing authorization and verify the correct owned-post read capability rather than assuming a similarly named developer scope fixes it. When app permissions were approved but the account token still fails, or when repair of the OAuth helper is separately authorized, follow [account authorization preflight and repair](account-authorization.md) for non-refreshing inspection, staged token validation and callback-readiness gates.
4. Keep lifecycle evidence distinct:
   - **PROCESSING**: accepted task, container, or remote ID without complete public verification.
   - **VERIFIED**: platform reports completion and an independent owned-post lookup returns the expected public URL.
   - **FAILED**: definitive platform failure with no uncertain remote outcome.
   - **NEEDS_ACTION**: missing verification permission, ambiguous/uncertain outcome, or a platform response requiring creator action.

   A task ID is not a publication receipt. For TikTok Business `business/publish/status/`, `PUBLISH_COMPLETE` with empty `post_ids` can precede indexing: keep the accepted `publish_id` and one-attempt history, perform a bounded status-only reread of that exact task, and do not infer a post ID from Studio timestamps, views, or an unrelated owned-post search. If a unique ID appears, verify it with the authorized owned-post lookup and match account/content before any scoped ledger/Sheet reconciliation; if still absent, retain uncertainty/NEEDS_ACTION and never resubmit. For an accepted task still active, the installed worker’s tested branch defers an initially empty ID to bounded checks of the same task (480 checks or 24 hours), then fails closed for review; test both delayed-ID success and no-ID exhaustion with exactly one submission. This branch was mock-tested, not live-verified on a delayed platform response. Do not clear an existing live REVIEW_REQUIRED latch to simulate this path. A completion status plus post ID is still not VERIFIED without the public lookup. When the workflow requires published-image matching, read [published-image verification](published-image-verification.md) before diagnosing a mismatch or reconciling its scoped gate. A post ID and public URL alone do not satisfy that stricter gate. An inbox/draft handoff means the owner must finish in the platform app; do not describe it as automatic publication.
5. Persist first, mirror second. Save remote IDs, task IDs, attempts, timestamps, URLs, errors, and reconciliation phase in the durable ledger before updating Sheets or notifications. Treat Sheets and chat reports as mirrors: repair them from ledger evidence without reposting. Preserve confirmed platforms when another platform fails. After scoped reconciliation, read back the job's platform rows and mirror/notification receipts; a nonzero worker exit can reflect unrelated accumulated business warnings even when this job's existing-task lookup, ledger update and Sheet reconciliation succeeded. Report the job result and global health separately, and never replay the reconciliation or publication solely because the process exited nonzero.
6. Report once, consolidated by platform. Include only verified public URLs and label every requested target VERIFIED, PROCESSING, FAILED, or NEEDS_ACTION. If a stricter visual gate is blocked, state “published with public URL; image proof incomplete” separately from generic ledger status. Never claim whole-job success unless every requested platform and required verification gate is complete. Delivery uncertainty for the report is separate from publication state and must not trigger a republish.
7. Test without public writes. Use fake platform clients and temporary ledgers to cover one approval/all targets, one submission per platform, restart after task acceptance, `PUBLISH_COMPLETE` with empty IDs followed by a unique owned post (and a bounded no-ID exhaustion), missing read permission, creator-action handoff, partial success, Sheet failure, notification uncertainty, and repeated recovery. Run a real dry-run only if it proves zero credential-sensitive writes, media submissions, platform POSTs, and Sheet writes.

Completion evidence: immutable approval binding, one attempt history per submitted platform, remote status and owned-post URL checks, any required visual gate, reconciled ledger and mirrors, duplicate-safe replay tests, and the exact remaining verification, permission or creator action for each incomplete target.
