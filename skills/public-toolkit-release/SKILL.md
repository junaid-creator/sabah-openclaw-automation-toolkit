# Public toolkit release

## Portable installation boundary

Read [README.md](README.md) before executing this procedure. The authored
reference workflow below describes diagnostic evidence and safety gates.
Reference script names, table names, job prefixes and state paths are schema
examples, NOT commands shipped or activated by installing this skill. Map them
to the configured deployment first. Missing adapters are blockers; do not invent
commands or bypass authorization. This package is a procedural skill, not the
complete underlying engine.


Use for an authorized source-code release, not business-content publication. Publication destination, license choice, production-preservation constraints and coverage targets come from the current request; this procedure grants none of them.

1. Establish a release register before copying code. On continuation, verify the current public HEAD/tree and reuse the saved source register rather than repeat completed discovery. Resolve source identity before grouping by dependency or function: common basenames such as index.js or SKILL.md are ambiguous, and a service ExecStart can point to bundled runtime code rather than an original adapter. Use resolved paths and content hashes, retain a mapping from every discovery record to its canonical group, and distinguish procedure, engine, wrapper and test roles. Separate original implementations, upstream references, unresolved rights and adaptation work; counts of records, modules, skills and functional groups are not interchangeable. A local file, an absent license header or a working installation does not prove redistribution rights. Resolve provenance before assigning a license; exclude unresolved material with a specific reason. Completion: every discovered in-scope record has an origin, dependency, evidence limit and release decision.
2. Build an allowlisted candidate outside production. Record source hashes and permissions, then adapt only selected copies. Exclude live state, history, identity material, customer data and private assets rather than bulk-copying a workspace. Make dependencies and configuration explicit; distinguish runnable modules from procedural skills and upstream integrations. A coordinating skill that requires a separate checkout must document that dependency and cannot be advertised as self-contained. For large registers or source files, check read truncation/continuations before using tool-returned text as a replacement. Prefer targeted edits or a deterministic local transformation of the complete file; compare the diff and record/path counts before committing. If a staged rewrite drops an inventory tail, recover the full pre-edit file from the validated Git object or backup and reapply only the intended change, preserving any newer edits. Completion: each included file has reviewed provenance and a portable installation/use contract; unported engines remain explicitly unported.
3. Reproduce the documented installation and the actual CI directory layout before acceptance. Use synthetic fixtures, temporary state and denied/mocked business egress. Run tests, skill validation, data-format/link checks and a secret scanner over the release candidate and clean Git history; review dotfiles and workflow permissions too. For new or updated dependencies, inspect release metadata including Requires-Python, update the advertised runtime floor when necessary, and verify that the tested environment actually matches the published pins. Syntax/frontmatter and helper-fixture tests validate only those artifacts, not a live procedural skill or a complete injected-adapter workflow. Scan source artifacts separately from installed dependencies. If CI creates a root .venv, a source gate that recursively scans it can reject interpreter symlinks, binary wheels and certificate bundles even though all application tests pass. Either install outside the candidate or exempt only that exact installation root while rejecting any tracked .venv root or descendant. Do not globally ignore all directories with that name or suppress source-file violations. Test both the normal installed environment and a negative fixture with a tracked environment artifact. Completion: the exact documented layout passes, the negative fixture fails closed, and failures remain in the verification record.
4. Verify an existing authorized GitHub identity and destination before remote changes. Check usable browser profiles/tabs as well as an already-authorized CLI: a disconnected extension profile does not prove a managed browser is unavailable, and a previous signed-out state is not current identity evidence. Inspect only required visible controls and secret-free account metadata; do not return whole form HTML, hidden inputs, CSRF values or cookies. Check whether the repository exists before creating or updating it. Respect upload-policy boundaries; use only an authorized staging mechanism and stop if none is available. Completion: actual account, repository ownership, intended visibility and approved upload manifest are known.
5. Verify published bytes independently of the upload result. Record the reviewed local commit and root tree with git rev-parse HEAD and git rev-parse 'HEAD^{tree}'. Browser-created commits can have different SHAs because their author, timestamp or message differs; compare the remote root tree and complete path set with the local tree instead of demanding commit-SHA equality. An exact tree match verifies names, modes and blob content recursively. Use unauthenticated GitHub metadata/readback and a fresh public clone to establish public access, then rerun the tests from that clone. Never export the private original Git history. Completion: public owner/visibility, actual remote commit, exact tree/path match and fresh-clone results are recorded.
6. Inspect CI and security results for the final remote commit, not just the first upload or an earlier successful run. If CI fails, read the failing step and distinguish application-test failures from artifact-gate failures; reproduce and repair the exact cause without weakening unrelated checks. Revalidate the correction, publish only the reviewed delta, then compare the new tree and final-commit checks again. Enable only authorized available security features; paid AI scanning is not implied by security review. Read findings separately from feature-enabled state: passing CI/CodeQL and a clean secret scan do not establish that the dependency graph has finished or that Dependabot has no alerts. If an advisory appears, inspect its affected range, patched version and actual usage separately. When a compatible patch is available within scope, update only the staged dependency environment, rerun tests and pin checks, publish the reviewed delta, and verify the alert is Fixed on the new public commit rather than dismissing it because the affected helper is unused. Recheck protected source hashes/permissions and report their bounded scope, not that all live runtime data was frozen. If the earlier baseline has drifted, preserve both evidence sets, leave unattributed changes untouched and state exactly which files differ. A later snapshot can bound subsequent checks but cannot retroactively prove the whole task made no changes; combine file comparisons with the actual actions and service start/generation evidence. Completion: final-commit CI/security evidence, public install instructions, excluded/adaptation counts and unchanged-source checks are explicit. Keep coverage separate from release quality: a source-derived helper does not complete its original engine, and documenting every group does not complete unfinished adaptation. Preserve incomplete groups and concrete dependencies in the canonical register; a verified portable subset remains PARTIAL when the requested complete-library coverage is not met.
