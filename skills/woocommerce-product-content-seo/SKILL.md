# WooCommerce product content and SEO

Use for an authorized product-copy/SEO optimization, duplicate-description diagnosis or product-image alt audit, not source-sheet synchronization, pricing, publishing, unrelated theme repair or a standing catalog-maintenance policy. For variation/transaction price semantics use [price display audit](../woocommerce-price-display-audit/SKILL.md); for cart/checkout rendering or payment-option visibility use [cart and checkout diagnosis](../woocommerce-cart-checkout-diagnosis/SKILL.md); for source-to-catalog sync, merges or uncertain commerce writes use [catalog reconciliation](../woocommerce-catalog-reconciliation/SKILL.md).

1. Read the full current catalog across relevant statuses and all pages, including every variation. Classify published products versus drafts and identify long-copy gaps, existing SEO fields, categories, options, media and price-bearing claims. Do not infer a rental period, capacity, accessory, stock or performance rating from generic copy, image or option label; preserve confirmed option/transaction distinctions. Define the exact in-scope product IDs and fields before editing. A request to improve published products does not publish a draft.
2. Take a protected pre-change snapshot of complete parent and variation representations plus the SEO metadata, and verify its integrity. A REST snapshot is a field-recovery artifact, **not** a database restore test. Prepare product-specific descriptions, concise short copy, distinct title/description/focus keyword, and relevant internal links to actual product URLs. Preserve useful existing long copy rather than replacing it merely to reach a word count. Keep slugs, prices, stock, variations, images, status and other commerce fields out of the write payload. Check each internal link before treating it as verified.
3. Use a bounded canary before the catalog-wide pass. Before each write, reread that product and compare planned content, SEO and protected fields to the frozen before state; stop on unexplained drift. Submit only changed content fields and explicit SEO metadata. After an uncertain PUT or verification interruption, inspect the live product before retrying: if intended fields already landed and protected data matches, perform read-only verification and record the result without another PUT. Never reset the checkpoint or repeat a write just because the response/readback failed.
4. WordPress may reformat stored HTML on save (for example, newlines around list items and paragraphs, or a trailing newline). When exact string readback differs, inspect the actual diff and use a **narrow markup-equivalence comparison** only for harmless whitespace between tags. Still compare text, links, attributes, tag order, all SEO values and protected fields exactly; do not blanket-ignore content changes. Test a genuine text/link/price difference as a negative case before generalizing an equivalence rule.
5. Verify each product via authenticated readback and the public URL: intended title, description, visible product content, canonical, product-specific structured data and cart form as applicable. Check the **number and values** of rendered `meta name="description"` tags; a correct Rank Math first tag does not make a second tag harmless or fixed. Record duplicate tags as a separate site-level defect rather than changing theme/plugin output under a product-copy request. If site-level repair is separately authorized, use [duplicate-description diagnosis](duplicate-description-diagnosis.md) to trace the second emitter and verify its narrow setting-based correction. Compare every captured variation and protected parent field against the backup, and leave out-of-scope drafts untouched. Use a real browser for representative desktop/mobile layout and option/cart checks when needed; an HTTP 200 or cart form alone is not checkout proof. Keep rendered-cart evidence separate from Store API state and checkout testing.

Completion: counts and IDs for audited, updated and skipped products; exact changed-field counts; protected parent/variation comparison; public URL/SEO evidence; backup integrity; and explicit unresolved site-level findings and untested checkout/restore boundaries. For an authorized image-alt audit, count both product-image references and unique attachment IDs; shared references are not separate media. Before any attachment edit, inspect the actual image and cross-use (featured image, other product/gallery and content). Change only verified, appropriately scoped media metadata with its old value backed up, then read back attachment and rendered alt; leave uncertain or broadly reused images for review. Do not infer visual details from a filename or product title. Changing attachment metadata needs its own scope because media may be reused.
