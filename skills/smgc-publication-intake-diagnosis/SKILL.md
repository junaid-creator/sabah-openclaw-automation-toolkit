# reference-workflow publication intake diagnosis

## Portable installation boundary

Read [README.md](README.md) before executing this procedure. The authored
reference workflow below describes diagnostic evidence and safety gates.
Reference script names, table names, job prefixes and state paths are schema
examples, NOT commands shipped or activated by installing this skill. Map them
to the configured deployment first. Missing adapters are blockers; do not invent
commands or bypass authorization. This package is a procedural skill, not the
complete underlying engine.


Use when an owner-approved SM-XXXX job never published or never reached the durable queue and the failure stage is unknown. This procedure is read-only: it does not approve, publish, schedule, edit Sheets, or restart services. For reconciliation after a job already has a ledger receipt or a partial/uncertain platform outcome, use [multi-platform-publication-recovery](../multi-platform-publication-recovery/SKILL.md).

For a supplied attachment rejected before a draft/job exists, use [supplied image intake](../supplied-image-intake/SKILL.md) to distinguish staging-path rejection from permissions and to resume the same request. Its repair branch requires separate authorization; this diagnostic remains read-only.

1. Preserve evidence before touching anything. Work from a checkpoint directory outside live state; never write to live files during diagnosis. If a prior repair attempt may have run, use its manifest or inspect its actual backup hierarchy before comparing files with live modules. Both flat backups and preserved relative-path trees occur; a wrong base path or filename pattern can compare nothing and falsely look unchanged. Record which files and protected tables were actually compared, retaining hashes and original approval data.
2. Confirm the draft exists and what it froze: `data/social-creative/history.json` (job → template, asset path, sha256, created time) and the `data/social-requests/*.state.json` that names the job (`completed`, `verified`, notification metadata, `url`, effective manifest with per-platform captions). Missing notification data or `notify_owner:false` means this state file does not prove delivery; a later messaging-tool preview may exist independently. Validate that evidence with [automation-adapter-verification](../automation-adapter-verification/SKILL.md), rather than concluding that no preview was ever delivered.
3. Read the current Sheets queue row without writing. Inspect the installed check/status entry point and its exception handling before invoking it: a nominally read-only branch can share an error handler that drains notifications. Use the existing Sheets read adapter without approval, recovery, reconciliation or notification calls when helper effects are not read-only. `WAITING_APPROVAL` + `eligible` describes the current row, not proof that no earlier approval or schedule existed.
4. Inspect the application ledger at `integrations/smgc-meta/publish-ledger.sqlite3` with Python SQLite using a `file:` URI and `mode=ro`; this worked without the SQLite CLI. Include `publication_jobs`, `publication_operations`, `publication_events`, `publication_schedule`, `meta_posts` and `publication_owner_actions` where present. Do not instantiate a ledger class merely to inspect it: constructors may migrate schema. For a consistent backup, use SQLite’s backup API from the read-only connection, not a plain copy that can miss WAL state; never restore it over live state. Respect an actual access denial rather than copying around it. If job-specific rows are absent across receipt, operation, attempt and event tables, investigate intake; do not infer that remote publication never occurred from local absence alone.
5. Map the installed timers to what they actually scan. A receipt-driven recovery worker cannot discover a missing approval merely because a Sheets row is due. Inspect the service entry point and due-job selection instead of running `recover` as a diagnostic: even its idle branch may synchronize notification events and drain an outbound transport. Check both system and user timer inventories for a separate Sheets scanner. A notification-only timer or watchdog is not proof that publication dispatch is enabled.
6. Locate approval evidence independently of the ledger: `sessions_search` for the job ID plus approval wording, then bounded `sessions_history` on the hit. If a trusted inbound instruction has no matching receipt, inspect the approval bridge and its admission result. Receipt absence does not distinguish unwired intake from a correct rejection of missing review evidence, stale content or unsupported timing. Inspect all-target asset validation in the approval-binding path too: one platform’s incompatible image can reject intake before any platform receipt is created. Run the installed pure media validators on the frozen local files with the application interpreter, recording decoded dimensions and exact failures separately from permission checks. Successful preview delivery is not platform-media compatibility. Do not recommend approving the unchanged all-target job as a way to publish only its otherwise-ready platforms. A reduced target set needs explicit owner authorization and verified helper support; for separately authorized implementation on an unapproved, unattempted draft, use [review target reduction](../automation-adapter-verification/review-target-reduction.md). Do not promise that different approval wording alone repairs missing subset support. A resized derivative changes the asset hash and needs a new exact-content review; for an authorized revision of an unapproved delivered draft, use [review media revision](../automation-adapter-verification/review-media-revision.md). Preserve the original asset and any existing approval rather than silently replacing either.
7. Check scheduling-code wiring before blaming parsing: a `scheduled_publication.py` module can exist and pass tests while nothing calls its `schedule()`; grep for call sites in the CLI and engine. Note that the approval path (`Engine.approve`) rejects rows carrying `publish_date`/`publish_time`/`timezone` (`IMMEDIATE_MANUAL_JOB_REQUIRED`), so a scheduled approval needs a distinct intake route — if none is wired, that is the root cause.
8. When a reviewed draft cannot enter the secure schedule path, inspect `reliability_cli.py:local_review_snapshot` and `secure_schedule_command.py`, not just call sites. Requiring delivered-review evidence is a safety gate, not a defect to remove for `notify_owner:false`. Never synthesize `local-preview:<channel>:<inbound-id>` from creation provenance. If genuine later delivery exists but the saved approval still references invalid evidence, name the missing supported existing-job reassociation operation; editing the original notification or approval JSON is not a repair. Distinguish this from a hard-coded job rejection or blanket platform exclusion: those need generic eligibility checks, with platform permissions retained. Any admission repair is separately authorized work with backups and regressions; it is outside this read-only diagnosis.

Report the failure as one named stage — draft, notification, Sheets write, approval bridge, ledger intake, scheduler wiring, worker, or platform — with the evidence for each cleared stage. Recommend the minimal reversible fix with a backup, but do not apply it under this procedure.
