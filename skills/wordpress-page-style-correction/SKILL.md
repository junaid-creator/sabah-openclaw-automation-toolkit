# WordPress page style correction

Use for a specifically authorized **page-level visual/CSS correction**, not a sitewide theme change, Elementor rebuild, copy/SEO edit or recurring maintenance. Confirm the target page ID and permitted fields; do not infer standing design policy from one job. For additive post/page copy use [WordPress additive content update](../wordpress-additive-content-update/SKILL.md); for product copy/SEO use [WooCommerce product content and SEO](../woocommerce-product-content-seo/SKILL.md); for theme switching use [WordPress child-theme readiness](../wordpress-child-theme-readiness/SKILL.md).

1. Inspect the named live reference pages and target in a browser. Record computed colors, fonts, backgrounds, corners, spacing, buttons and FAQ behavior from the relevant elements rather than guessing from screenshots or merely copying HTML. Inspect the target’s edit-context REST record and public response; verify ID, slug, status, template, raw content and whether Elementor actually owns the page content. A page using an Elementor header/footer template may still have empty Elementor data and an embedded `style` block in `content.raw`. Save the complete edit record and public HTML before mutation as scoped rollback evidence; do not expose authentication values.
2. Construct the replacement CSS only within the existing page wrapper. If the page owns one embedded style block, replace just that block and assert the rest of `content.raw` is identical after substituting both style blocks with the same placeholder. Preserve headings/copy, links, image attribution, structured data and FAQ elements. Keep shared header/footer, sitewide widgets, theme CSS and other pages outside the selector scope. Stage the candidate and hash it.
3. Preview in a disposable browser tab without writing WordPress. When the original stylesheet is an inline `style` later in the body, appending preview CSS to `head` can leave original equal-specificity rules in control; individual elements may appear corrected while others still use the old rules. Replace the *original inline style element’s text in the browser DOM* with the candidate CSS for preview, then inspect computed values. This is a local tab mutation only; a reload restores server state. If stylesheet order or ownership differs, inspect the cascade before choosing the preview method. Check desktop, tablet and narrow-mobile widths for content overflow, image loading, card/hero columns, FAQ open/close and keyboard focus, plus CTA destinations and hover.
4. Before an authorized write, reread the edit record and compare ID, slug, modified time and raw content with the backup; abort on concurrent drift. Send only the `content` field through the installed authenticated WordPress route, without embedding credentials in scripts or logs. Use the known working authenticated client before diagnosing a different client’s HTTP error as a permissions failure. After an uncertain write, read back before retrying.
5. Read back `content.raw` and compare its hash and exact bytes to the staged candidate. Compare non-style content and exposed metadata with the saved record. Fetch a fresh public response; verify SEO title/description/canonical/robots and schema unchanged, then reload a clean browser tab and repeat responsive computed-style, FAQ, link, image and overflow checks. A browser DOM preview is not proof of a live write; an HTTP response alone is not visual QA. If screenshot capture fails, report that limit rather than claiming visual screenshot verification.

Completion: saved rollback record, exact style-only diff, authorized write/readback, fresh public markup/SEO comparison and live responsive interaction checks, with any unverified visual boundary named explicitly.
