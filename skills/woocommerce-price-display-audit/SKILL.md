# WooCommerce price display audit

Use for a source/catalog price discrepancy or a badge that appears on shop cards but not on a product page. Diagnosis does not authorize price, discount, template, snippet, media or source edits. For Google Sheets access evidence, use [google-sheets-readiness](../google-sheets-readiness/SKILL.md). For authorized catalog/variation synchronization and uncertain-write recovery, use [woocommerce-catalog-reconciliation](../woocommerce-catalog-reconciliation/SKILL.md); for a cart/checkout loading or missing-payment-method defect use [cart and checkout diagnosis](../woocommerce-cart-checkout-diagnosis/SKILL.md). Display repair must not silently become catalog mutation.

1. Read the installed integration helper and live pricing implementation before assigning meaning to fields. Identify transaction categories, parent/variation attributes, discount fields and custom display snippets. In the reference implementation, Rent/Sell categories and `Purchase Type` distinguish transactions; WooCommerce `sale_price` is a discount within either transaction, while badge text “Sale” denotes selling. Verify that contract on the current installation; never map a source selling price directly to `sale_price` by its name alone.
2. Read all relevant parent and variation IDs, statuses, SKUs, attributes, regular prices, discount prices, effective prices, sale dates and stock settings. Keep IDs through comparisons. Raw parent `_price` metadata can contain multiple rows for a variable product: collapsing metadata to a single key/value loses prices and may leave a maximum rather than the REST effective minimum. Use the supported product/variation representation and individual variation values for comparison; do not call those repeated parent rows duplicate products or price corruption.
3. Match each source option plus transaction to its actual variation. Report effective-price differences separately from regular/discount differences and missing options. Duplicate source combinations with different prices require a decision, not last-value-wins parsing. A source amount can establish a target transaction price without deciding whether to retain an existing regular-price anchor or remove a discount. Check long/short descriptions and price-bearing SEO for the same conflict, proposing only necessary edits.
4. Fetch public product pages without cart or order mutations. Compare embedded variation data with authenticated reads. Inspect badges by the exact product ID (use the current installation’s configured product-marker attribute), not by the presence of any badge in the HTML: related-product loops can show correct badges while the main product has none. Check shop cards separately. When crawling WooCommerce pagination, normalize the first-page alias (for example, `/shop/?product-page=1` and `/shop/`) before enqueueing and deduplicate visited pages. Count cards only after exhausting unique pages: revisiting the same first page can falsely report duplicate products. Preserve other query filters rather than collapsing distinct catalog views. HTTP 200 and correct variation JSON establish neither visual layout nor cart/checkout correctness. In a real browser, use the form’s Clear/reset control before each affected combination, then select its options. A previous Sell selection can disable a rent-only technical option; failure to select it is not evidence that the variation is missing. Wait for both the expected variation ID and the final rendered effective amount: the hidden ID can update before the animated price. For discounted prices use the final effective amount, not the crossed-out regular amount. Extract the numeric token from the amount element and compare exactly using the site’s separators; stripping all non-numeric characters can retain punctuation from an Arabic currency symbol, and substring matching can accept the wrong larger amount. Check desktop/mobile badge visibility, bounds and screenshots separately.
5. If non-discounted products alone lack their own-page badge, inspect the active Elementor product template, the installed product-images widget render method and the badge hooks together. The observed Pro Elements widget calls the sale-flash template and product-image template directly, bypassing `woocommerce_before_single_product_summary`; the reference implementation’s non-discounted fallback was attached to that bypassed hook. Shop-loop badges still worked. Confirm this path against current source and HTML before attributing the defect; it is not evidence of wrong prices. Never introduce fake discounts to trigger a display hook.
6. Report database/API pricing, main-product badge, shop/related badges and browser/cart verification as separate results. Recommend a scoped display compatibility change only when the rendering mismatch is evidenced. Any implementation requires separate authorization, a snippet/template backup, and tests for discounted and non-discounted products, Rent-only/Sell-only/mixed options, unavailable variations and exactly one badge per intended location. Preserve commercial values and media.
   For the verified Elementor bypass, an append-only `elementor/widget/render_content` filter can reuse the existing badge helper: restrict it to `woocommerce-product-images`, respect the widget’s `sale_flash` setting, require the current eligible non-discounted product and actual gallery markup, and check that widget’s output for the current product marker before prepending. Do not globally suppress the product ID across shop/related widgets or alter gallery DOM. Scope any positioned-ancestor CSS to the image widget container. Back up and compare the exact live snippet before saving through the installed WPCode API; inspect its slashing/cache behavior and read back byte equality. Test the unchanged native/shop paths and the new path in isolation, then live, with a guarded original-code rollback if verification actually fails. A captured gallery fixture is not a full live-theme test.
7. Only when cart testing is authorized, follow [cart acceptance and cleanup](../woocommerce-cart-checkout-diagnosis/SKILL.md) for the fresh guest context, uncertain-add reconciliation, rendered-item checks and verified empty-cart cleanup. Compare selected variation IDs, quantities, minor-unit prices and totals. Keep the test within the authorized cart scope; the linked checkout branches do not authorize extending it. Never submit checkout/payment to prove a display fix, and report cart validation separately from an untested checkout.

Completion evidence: source-to-variation comparison with IDs, verified transaction/discount semantics, product-specific HTML checks, inspected rendering path for any diagnosed hook gap, and explicit limits on visual or checkout verification.
