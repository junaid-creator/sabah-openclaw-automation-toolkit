# Persistent asynchronous asset recovery

Read for an audit of an installed persistent image-recovery route, an explicitly authorized implementation that recovers without another chat turn, or a separately authorized historical manual catch-up. An audit or one-time recovery request does not authorize installing a watchdog, new inference, notifications or standing publication policy. The main skill owns asset verification; [automation adapter verification](../automation-adapter-verification/SKILL.md) owns runtime routing, scheduler scope and delivery.

1. Inspect the existing observer, service account, runtime registry, controller and notification consumers before adding a worker. Establish whether provider task results are durable: the inspected native media registry was an in-memory Map, not the scheduler task table. Do not invent a database lookup or use a current-chat status tool as an arbitrary historical-task API. Saved source files alone do not establish task ownership.
2. If authorized to add capture, persist intent before the native submission and the real typed task receipt afterward. Use one canonical intent format across hooks and worker. Bind current run, trusted session/tool-call identity, immutable brief/metadata and a cryptographically unique filename; preserve a durable in-flight claim when the response is lost. Confirm native filename normalization/truncation from installed source before using its prefix for output discovery. Capture only the actual structured task result, not a task-like string from prose. Reject conflicting receipts, cross-session rebinding and repeat launches. Repair a crash between saved receipt and controller binding from that saved receipt, never by guessing a task from a file.
3. For independent atlas processing, inspect dimensions and actual boundaries. A frozen separator contract with strict pixel detection can make cropping deterministic, but a visible band may split into extra detected groups when one antialiased row falls just below the full-width threshold. On rejection, read the exact run-bound source and contract, measure per-row qualifying fractions and consecutive-band lengths, and compare known passing atlases before blaming missing media or the provider. For an evidenced one-row interruption, an authorized detector repair may join adjacent high-confidence cores only when the intervening row is nearly full-width magenta (the verified case used >=0.98 versus >=0.995 for core rows), and the merged band still satisfies the original height, two-band, nonoverlap and minimum-panel gates. Do not globally lower the core threshold, infer equal thirds or accept ambiguous/missing markers. Trace the actual scheduled/observer route to the imported detector; native and CLI fallback may use different separator functions. Test the exact saved source and passing atlases through **each reachable route**, including a one-row near-full-width interruption, half-width bridge, missing band, bad dimensions and corrupt data. If the fallback rejects native-proven geometry, reuse the strict native result first while retaining the fallback’s separately bounded wide-band case. In temporary state, exercise crop → three distinct decoded, hashed WebPs → controller image receipt → frozen plan binding, and reject wrong task/source hashes. Verify source hash/stability and approved geometry before saving three assets with metadata. A latched REVIEW_REQUIRED does not clear merely because code changes or an offline detector test passes: separately authorized, audited operator reconciliation must bind the original task/source hash and observed crop geometry before continuation. Do not resubmit the image or treat an observation deadline as provider failure.
4. Extend the existing worker only within the authorized scope. Use per-run locks, durable attempts/backoff, immutable verified checkpoints and explicit review latches. Distinguish genuine activity from a stall using authoritative terminal receipts, operation locks, controller changes and active continuation claims; age alone is insufficient. Keep deterministic processing independent of model quota. When images complete after article/plan preparation, inspect both the daily artifact directory and the runtime directory beside the controller for saved preparation and article bytes before declaring the final frozen plan missing. Bind only the completed controller image receipt to the unchanged prepared copy, validate article-byte equality, run/date, image hashes and worker schema, then freeze one plan; never invent a replacement or generate again. A `NEEDS_AGENT` latch for an absent final plan must re-evaluate that saved preparation once images are verified, rather than waiting only for the final-plan file to change. Missing or mismatched evidence remains blocked; do not clear a `REVIEW_REQUIRED` latch or consume another model turn for deterministic assembly. Only genuinely missing model-required artifacts may enter a separately bounded, approved-model continuation path; preserve unknown launches rather than replaying them. Do not transfer a one-time day/cutoff or retry budget into a standing policy.
5. Test the real interfaces together, not only permissive mocks. Feed worker-produced evidence into the actual admission validator: required full-controller hash/mtime fields and artifact paths must agree. A scheduler receipt UUID is not automatically an agent run ID; recheck it against its own exact receipt store, and use agent wait APIs only for actual accepted agent-run IDs. For an unclaimed request surviving downtime, revalidate unchanged controller evidence and current authoritative inactivity before admission; never refresh or reclaim an already CLAIMED/UNKNOWN launch. Preserve the original evidence and the fresh admission check.
6. Verify execution through the deployed service environment and interpreter, not the interactive chat. A harmless one-shot service-context probe can establish account identity, atomic artifact writes, image tooling, read-only task data and required authenticated readbacks without granting new root access. Inspect existing privileges before adding sandbox flags that could break an intentional narrow read-only helper. Back up and merge the existing unit; test temporary checkpoints, crash/restart, active-provider preservation, wrong bindings, missing assets, remote uncertainty, independent alerts and repeated recovery. For a recurring daily publication observer, test consecutive local dates with distinct run IDs in isolated state: an earlier day's protected latch must not block a fresh day, and retries after an uncertain post or Sheets timeout must reconcile without another publication. Its COMPLETED predicate must require the verified publication checkpoint, matching date/post in the append-only publication ledger, and the bound reporting outbox. Compare the ledger publication URL and result with the actual public WordPress readback: an append-only publication event may inherit a draft preview URL and stale draft-status text even while the post, Sheets and owner notices are correct. Preserve that event and, when correction is authorized, append a separately keyed reconciliation record with the verified public URL; never edit the historical row or repeat publication. Verify Sheets from independent readback when claiming a synced mirror, not from outbox wording alone. Include missing-ledger, stale-preview-URL and repeated-tick negatives. Block network/business writes in fixture tests and compare protected production state afterward.
7. Accept each boundary separately: source installed, interface tests passed, service active, actual service invocation/health recorded, hooks registered in the committed plugin generation, and real provider completion observed. A completed-run service no-op with writes:false proves the worker can execute safely in that context, not that future generation or publication will succeed. Pending plugin drain or mocked hook capture must remain unverified. Preserve the original daily schedule and protected completed jobs.

## Historical manual catch-up

Use only on a separate explicit owner request to publish a specific interrupted daily article when the ordinary route is date-gated or latched. This is not a standing backfill policy and does not clear the old run. The verified November 2026 path used a one-time journal rather than editing the original checkpoint.

1. Bind the original article bytes/hash, saved plan, native task ID and unique completed atlas path/hash. Fully decode and detect observed separator geometry with the current strict detector; save three distinct WebPs with decoded dimensions, actual-byte hashes and descriptive metadata. Check live WordPress across statuses, the ledger, and all tracker tabs for title/slug/keyword/date duplicates before any remote write.
2. Freeze a separate catch-up identity and immutable plan/provenance in a durable, globally locked operation journal. Use create-once media and post operations with stable IDs and readback; an uncertain creation without ID remains review-required, not a retry. Read back content, taxonomy, image metadata and SEO before one journaled publication POST. An uncertain publication is reconciled by authenticated GET, never a second POST. Do not reset the original REVIEW_REQUIRED state or mark its controller complete.
3. Before the publish write, verify all three public image hashes; afterward, verify the canonical public URL, full saved content and Article schema. Record the actual publication time (never backdate), one separate ledger run and idempotent Sheet upsert/log with independent three-tab readback. Send the verified manual-catch-up result to each authorized owner channel through its own message-tool claim and receipt, preserving unknown delivery without resend. Inspect the live post again for uniqueness and confirm the old latch is unchanged.

An isolated copy of the old image/plan stages can test the detector and downstream binding with network and production writes disabled; that proves local recovery only. It does not authorize changing the old run or prove a future scheduled execution. Keep scheduling and notification mechanics with [automation adapter verification](../automation-adapter-verification/SKILL.md).

Completion: canonical intent/receipt contract, verified asset outputs, cross-component replay and admission tests, actual service-context proof, committed runtime registration or exact activation blocker, and clear remaining external validation gates.
