# Unattended poster acceptance audit

Read for a test-only acceptance audit of an **installed recurring social-poster series** across templates, daily assignments, semantic review and multi-platform recovery. This is not template installation, a new draft, or approval to publish. For a new template package use [poster-template integration](../poster-template-integration/SKILL.md); for an existing rejected job use [same-job poster revision](../generated-asset-checkpoint-recovery/same-job-poster-revision.md); for actual platform uncertainty use [publication recovery](../multi-platform-publication-recovery/SKILL.md).

1. Freeze the baseline before tests: hash installed renderer, CSS, brand assets, reviewer and worker; read the locked-template manifest, live series cursor/assignments and image eligibility through a read-only SQLite connection, plus the timer's next local elapse and actual ExecStart. Read the SEO schedule, existing failed review hashes, current channels, integrity guard and relevant publication/notification worker status. A failed old service invocation and a later recovered job can coexist; report them separately. Do not run the publish-capable service or recovery drain as a diagnostic.
2. If a long test must outlive the chat turn, establish an independently supervised bounded runner before starting work. Verify a transient service can write checkpoints under a private test root; use a no-restart unit with a finite runtime. For offline render, rotation, unit tests and mock publisher, mount production read-only, bind only the test root writable, and disable network. Probe the boundary rather than assuming systemd's ProtectSystem alone makes the user's home read-only. Keep test logs and intermediate receipts even when an environment setup fails. Pin the existing Playwright browser cache explicitly when HOME is isolated; tests that intentionally read the installed owner config need that config visible **read-only**, not copied secrets or a writable production HOME. Keep genuine model review in its own bounded runner with only the necessary provider access and test-root writes; no provider call is implied by offline renderer success.
3. For each template, render a uniquely named local JPEG from a category-matched atlas or photograph and frozen campaign copy. Preserve one poster/QA record/output SHA per template, and check decoded size, fit/overflow, original brand/contact data and QR destination decoded from the **final JPEG**. Template-specific QA schemas can differ: before invoking the recurring daily reviewer, compare its required keys and branding/scene contract with each renderer's actual QA output. An isolated dual-company renderer can pass its own QR and layout checks while the shared daily reviewer rejects it as RENDERER_QA_FAILED before inference; that is an admission defect, not a semantic failure or renderer failure. Do not map keys mechanically or weaken logo/contact checks to force admission.
4. Run the actual objective gate with test job identities and the intended scene checkpoint. If the task authorizes semantic inference, submit the actual renderer-specific inputs through its compatible reviewer (five scenes for the catalog route; a one-hero dual-company layout needs its own proven gate), at most once per exact artifact. Before invoking a one-off reviewer, inspect an actual inference envelope and persist its raw response under the attempt identity before parsing or validating it: the observed CLI input list contains paths and MIME types, not SHA-256 fields. Hash the local input bytes before and after inference, compare the envelope’s ordered input paths/provider/model with the submitted files, and retain the binding, attempt, raw result and decision. If capture or provenance validation fails after a provider call, mark the verdict unknown, reconcile only saved raw evidence, and never resubmit identical bytes to obtain another answer. Do not fabricate five-scene evidence to force a different template through the catalog gate. Preserve every FAIL and its hash. Before any new inference, compare the candidate final JPEG SHA256 with all saved failed outputs for the series, not just the current job ID or filename; a new test identity or renderer change that yields the same bytes is not a new review opportunity. If a repeat PASS was already obtained on identical failed bytes, retain it as conflicting evidence but exclude it from admission and mock publication; do not clear the original latch or derive PASS from positive subchecks. When an image viewer suggests clipping, corroborate against a local decoded final image and byte hashes before diagnosing a renderer defect or changing capture code. Only actual PASS receipts may enter an isolated scheduled-approval and publisher simulation. For a claimed combined end-to-end acceptance, exercise the canonical preparer with a **fresh** product-specific artifact through its real scene generation, render and semantic gate; a reused same-product/template PASS with the preparer or upload mocked proves only the downstream integration. Category-ambiguous equipment names need an explicit mechanism/application brief for every scene, not just a correct featured image; inspect all new cards before calling the product ready. If the fresh artifact FAILs, preserve its exact hashes and attempt, identify rejected scene indices, and verify the installed same-request retry does not mint another job or resubmit the identical review. Mock every external platform/Sheet/notification write and use network denial for that simulation. Verify one call per requested platform, zero calls on replay, and zero calls for an actual failed quality gate; mock URLs are never public publication receipts.
5. Run date/rotation simulations only in isolated ledgers. State whether they exercise reservation mathematics, complete draft/review/publication cycles, or both; assignment rows are not independent posters or semantic approvals. **When the series promises every published product in storefront order**, reconcile IDs across all public shop pages with the complete read-only WooCommerce parent catalog. Neither ascending IDs nor image eligibility establishes display order. Freeze that order per cycle, refresh only at a checked boundary, and test the independent product/template cursors through their least-common-multiple pair cycle. Keep image source/category/rights evidence separate from inclusion: reserve the intended product even with a missing, wrong-category or unreviewed image, record an unresolved reason, and block its publication rather than silently substituting another product. For a live order correction, rehearse a guarded forward-only migration on an online SQLite backup; preserve earlier assignments and platform receipts, handle already-assigned legacy identities without reposting, and test next-date/wrap/duplicate reservations and missing-image identity. Do not restore an old ledger over newer work. Synthetic rotation coverage does not prove real catalog eligibility or per-template visual PASS.
6. Exercise fault cases with mocks or disposable assets and classify each as blocked safely, recovered safely, failed, or **not exercised**. Include review missing/FAIL/timeout and hash drift, partial platform success, uncertain remote results, delayed TikTok IDs, Sheet/notification failures, restart and replay. Positive QR/fit checks do not prove negative malformed-QR or clipped-copy injections were run. Compare production source hashes, cursor, assignments, eligibility and historical FAIL artifacts against baseline; confirm temporary runners stopped and no new timer exists. Deliver a per-template semantic matrix, simulation scope, fault results, production readback and a readiness verdict. An enabled timer, passing unit suite, or a subset of accepted mock posts cannot establish all-template unattended readiness.
