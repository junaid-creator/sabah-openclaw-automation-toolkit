# Restricted command bridges

Use when implementing or accepting an owner-only deterministic chat command adapter. This branch supplies implementation checks; the main skill owns trusted identity, approval provenance and real delivery evidence. It grants no installation, configuration or mutation authority.

1. Before implementation, compare required admission facts with both the installed pre-dispatch types and the actual channel-to-hook mapper. Parse only canonical command content, not an expanded agent body or quoted text. The inspected `before_dispatch` types and mapper omitted forwarding provenance despite exposing sender, group and reply fields. Absence is not false: if the owner policy explicitly requires rejecting forwards, keep admission blocked until the host supplies that fact; otherwise an exact job command from the authenticated, allowlisted owner in a separately verified private conversation may be admitted without inventing `isForwarded:false` or claiming that forwards are rejected. Require trusted channel, account, sender, independently matching private conversation, explicit non-group fact and message ID. A WhatsApp self-chat can use a numeric `@lid` address rather than the owner's phone-number address; accept that direct-chat shape only alongside trusted owner checks, and reject group/broadcast addresses and group session keys. When the protected backend expects a phone-number conversation identity, normalize an accepted LID to the **authenticated sender** only after that direct-chat check; passing the raw LID through a natural-language hook can pass its admission yet fail the backend owner check. Normalize only aliases established by source evidence, and test hook admission and backend acceptance together. Passing local tests is not proof that the changed plugin generation loaded. Reject malformed owned-command syntax and unauthorized callers before invoking the worker; unrelated customer/blog/social messages must fall through unchanged. Register no general agent tools merely to run this adapter. Test missing forwarding metadata on both owner channels, forged event/body identity, wrong account, missing fields, self-chat LID, groups and ordinary-message fallthrough. Mock admission and a loaded plugin do not prove a genuine owner inbound command was handled.
2. For a host-provided one-shot admission/revalidation callback, claim it exactly once at the protected handoff and **await** it before starting the child process or writing JSON stdin. Do not preclaim in the natural-language handler and then claim again in the bridge; do not call an async owner check without awaiting it. Test a callback that rejects asynchronously and assert zero child launches, plus a one-shot callback that fails on a second call. Then launch a fixed executable/script with JSON stdin, no shell and bounded input/output/time. Exercise a harmless real read through the **same worker environment**, not only an interactive shell. A verified GOG bridge failure reported missing account under a clean environment despite working ordinary reads: narrowly forwarding the existing trusted `GOG_KEYRING_BACKEND` and `GOG_KEYRING_PASSWORD` restored access; forward `GOG_ACCOUNT` only if configured. Confirm required variable presence without exposing values. Do not inherit arbitrary loader variables, dump environments, rotate credentials or add a blanket dotenv/shell loader. Decode streamed stdout incrementally so split UTF-8 does not corrupt valid JSON.
3. Treat subprocess timeout as uncertain, not proof of cancellation. On Linux, a dedicated process group with validated positive child PID permits best-effort termination without signaling the Gateway group. Test an actual same-UID descendant using a temporary delayed writer, plus fake/unsafe PID rejection. Different-UID sudo descendants and remote operations can still survive. Persist phase intent and identity reservations before remote work; keep them after timeout and require outcome reconciliation before another job can target the same identity.
4. Where the workflow promises cancellation during execution, revocation must not wait behind the long mutation lock. Commit an owner-bound revocation independently, atomically order each new write-phase intent against it, and prevent receipt replacement from losing it. Acknowledge only persisted revocation; an already-started phase may finish, but later product/source/mirror phases must not start. Test with a held mutation barrier, concurrent cancellation, preserved remote IDs and zero subsequent writes. This does not replace a scheduled-publication policy that intentionally rejects active/claimed work.
5. Replayed messages must not repeat effects or resurrect stale approval prompts. Consult current durable job state when returning cached responses after cancellation, expiry, completion or uncertainty. Missing/stale/tampered plans fail before mutation. Test actual worker entry paths, not just helper predicates.
6. Separate acceptance layers: synthetic routing tests; real worker read under its deployed environment; isolated mutation/backup tests; runtime hook registration; genuine owner inbound command; actual reply delivery. Hook `handled:true`, listener health and an outbound test invitation prove neither the last two layers. Do not solicit a live approval as the next step while required admission metadata or activation is still unavailable; label any authorized preview delivery as review-only with the unresolved blocker. Correlate delivery conservatively by channel/account/recipient and exact reply identity; ambiguous identical replies remain unverified. After authorized activation, inspect registrations and scoped configuration delta; use actual generation/process evidence for any no-restart claim. Do not infer Gateway-wide restart requirements from one management tool’s limited activation surface, or bypass a tool-policy restriction because another documented route exists.

Completion: supported commands and refusal boundaries, passing negative/concurrency tests, real environment read, exact deployed registration/configuration scope, and separately evidenced inbound/reply results or a concrete owner-test gate. For product plans and recovery, use [approved row jobs](../woocommerce-catalog-reconciliation/approved-row-jobs.md).
