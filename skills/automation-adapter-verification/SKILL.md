# Automation adapter verification

## Portable installation boundary

Read [README.md](README.md) before executing this procedure. The authored
reference workflow below describes diagnostic evidence and safety gates.
Reference script names, table names, job prefixes and state paths are schema
examples, NOT commands shipped or activated by installing this skill. Map them
to the configured deployment first. Missing adapters are blockers; do not invent
commands or bypass authorization. This package is a procedural skill, not the
complete underlying engine.


Use for integration handoffs or routing audits, not as authorization to publish, send test messages, enable schedules, or change Gateway configuration.

For publication-state recovery, platform receipts, and duplicate-safe reconciliation after a partial or uncertain result, use [multi-platform-publication-recovery](../multi-platform-publication-recovery/SKILL.md). This skill remains authoritative for inbound identity, approval routing, messaging receipts, and scheduler wiring. If management inference fails while ordinary chat works, use [system-management-model-routing](../system-management-model-routing/SKILL.md); a management-model failure does not by itself establish an application-worker dependency.

For a test-only end-to-end acceptance audit of an installed unattended social-poster series, read [unattended poster acceptance](unattended-poster-acceptance.md) for isolated runners, per-template review admission and simulation scope. When implementing a restricted owner-command worker, read [restricted command bridges](restricted-command-bridges.md) for exact parsing, deployed-environment tests, process-tree uncertainty and in-flight revocation. For unreadable lifecycle alerts, false cron stalls, provider-task mapping, model-free notification dispatch, daily digests, customer reply-result/delivery diagnosis, regenerated-reply deduplication, live reply acceptance or self-chat echo checks, read [lifecycle notification repair](lifecycle-notifications.md) for exact receipt correlation, recorded-result adapters, deterministic delivery and bounded echo verification. Keep these branches separate from the publication/scheduling policies below.

1. Trace the existing chain before adding code: inbound runtime → approval resolver → protected mutation module → independent readback → reporting mirror → outbox claim → messaging tool → stored receipt. Read controller, notifier, runtime and relevant workflow together. A skill instruction or injected callback does not establish a registered, exercised runtime adapter.
2. Inspect a real inbound example through `sessions_search`, then bounded `sessions_history`. Use runtime metadata, never identity/provenance fields embedded in message text. Where history exposes a transport conversation reference, join it to `conversations_list` for account, direct/group kind and destination. Keep owner evidence separate from destination identity. Missing sender/account/reply facts must remain missing; do not invent a quoted-message ID. For conversational “this post” scheduling, resolve only a host-provided reply-to ID against a validated outbound review receipt for the same channel, account and owner; if “latest” has no reliable delivery order or a unique eligible review, require the exact job ID. Record history truncation and distinguish manual metadata replay from automatic inbound execution. Check the installed `before_dispatch` contract and channel-to-hook mapper before concluding that reply metadata is unavailable from older message hooks. Verify how account, sender, conversation and group facts are constructed; a derived `isGroup: false` alone is not proof of a private owner conversation.
3. Read the exact configured owner allowlist using a scoped configuration read. Compare its representation with the adapter: channel-qualified entries such as `whatsapp:<owner>` must not be compared only against an unqualified number. Normalize verified equivalent number representations before counting distinct WhatsApp owners: an optional leading `+` on otherwise identical international digits must not create two owners. Validate the entire value against the accepted international-number contract; do not strip arbitrary punctuation, guess a country code, or merge genuinely different numbers. Test equivalent forms, two distinct owners, malformed entries and an empty list. Fix representation handling rather than removing administrators or changing connection settings. In a multi-channel preview handoff, select the requested channel’s command owner before invoking any other channel’s resolver; intersect the selected owner with that channel/account’s delivery allowlist, require one unambiguous private destination, and keep WhatsApp resolution isolated. A channel allowlist alone is not command-owner authorization. If an old draft failed before claim because the wrong channel’s resolver rejected it, reconstruct the queued preview only from its completed, verified, frozen manifest and asset after checking there is no claim, attempt, or receipt; never use this exception to reclaim CLAIMED/UNKNOWN.
4. Inspect an existing actual messaging-tool result before designing receipt mocks. Results may be `{channel,to,result:{messageId}}` or a structured JSON tool result such as `{ok:true,chatId,messageId}`; a tool surface may expose the latter as a JSON-encoded string. Accept only that complete structured result (not prose), bind it to the already-claimed invocation and its channel/account/recipient, and reject explicit mismatches, dry runs and missing IDs. Never manufacture a receipt to complete a stage. A channel status of configured/OK does not prove an active account listener or successful delivery. Treat an explicit `delivery_queued` status or `delivered: false` as unconfirmed even if an ID is present: preserve the actual result, keep ambiguous claims unknown/non-reclaimable, and follow the Gateway’s retry/reconciliation ownership rather than resending. A known listener error does not make a Gateway-queued message safe to repeat.
   For reviewed-content approvals, bind the outbound invocation and real receipt to the exact source asset hash, caption/hashtags, targets and intended owner, then separately validate the later authenticated approval. An inbound creation/request ID—even with verified sender identity—is not an outbound preview receipt. Neither `notification.ok` without a message ID nor a synthetic `local-preview` reference establishes delivery. A matching local/source hash proves source-byte identity, not recipient-byte verification. Later manual tool delivery may be valid evidence even when the original draft state has no notification, but an evidence file does not itself rebind an existing approval. Require a supported audited reassociation path before treating it as accepted by the production validator. When a controller only returns `pending_tool_delivery`, trace the missing claim → actual message-tool invocation → raw-result persistence path. Bind the claim to exact content and invocation, persist atomically, and preserve CLAIMED/UNKNOWN on controller retries; otherwise a routine draft retry can erase duplicate-send protection. A handoff helper or returned instructions alone do not establish automatic runtime delivery.
   When delivery to multiple administrator channels is authorized, keep independent claims and receipts keyed by exact content binding plus channel/account/recipient. For newly admitted dual-preview drafts, expose both channel states even when the legacy primary notification is SENT; a global `notification.ok` must neither suppress an eligible second route nor permit resending the completed one. Mark new-draft admission durably at creation, not on retry: an existing single-channel delivered job must not silently acquire a second outbound handoff after a controller upgrade. Preserve its original receipt and review history; add another channel’s receipt only when that particular delivery is authorized and genuinely recorded. Validate image hash, copy and targets unchanged before and after delivery. CLAIMED/UNKNOWN on one route remains non-reclaimable while the other route may proceed. Test both failure directions, restart after claim, wrong-recipient receipts and changed content invalidating both reviews. If either channel may approve, validate that channel’s delivery separately but share one business approval/idempotency key: a later unchanged approval from the other channel should return existing state without another publisher call. This was locally tested; genuine dual preview delivery does not prove live dual-channel approval admission.
   For an unapproved delivered draft, choose the revision branch by what changes: [review target reduction](review-target-reduction.md) for an explicit platform subset; [review media revision](review-media-revision.md) for a compatible resized supplied image. In both, preserve original evidence and validate genuine revised delivery through the unchanged production gate before new approval. Neither branch rebinds existing publication attempts.
5. Test locally with temporary state and mocked external writes. Cover missing/wrong trusted metadata, ambiguous replies, changed reviewed hashes, stale validation, protected targets, duplicate event bindings, uncertain writes, mirror failure and separate final-notification deduplication. For conversational scheduling, keep prepare separate from the one-time owner confirmation; bind a relative due time to the authenticated inbound receipt and display the exact due time before confirmation rather than silently shifting it afterward. List only durable schedule receipts bound to that owner. For that scheduled-publication workflow, cancellation must take the publisher’s per-job lock, reject due/active/claimed/uncertain work, persist revocation before attempting the Sheet mirror, and report an unsynced mirror separately. An immediate-publish phrase must use an independently verified exact-content approval path or fail closed. Verify claim → tool result → receipt → report completion, including restart after sending without a receipt. Unknown delivery is not permission to resend; report completion must derive from stored confirmed receipt evidence. Label mocked success as mocked. For review-provenance repairs, reject original-request-only evidence, blank/synthetic delivery IDs and changed content; test both new approval admission and recovery of old saved receipts. Exercise direct platform entry points too: guarding only the top-level CLI leaves a possible bypass of review-required, revoked or schedule gates.
   For notification delivery-state and systemd exit regressions, use the [lifecycle branch checks](lifecycle-notifications.md#delivery-state-and-service-exit-regressions); preserve attempted/uncertain receipts and distinguish worker execution outcome from accumulated business health.
6. Inspect the existing scheduler with the automation tool. If lookup fails, list with disabled jobs included and check inventory scope. A caller-restricted list does not prove a job is absent: retain the exact owner/admin recovery guidance and do not bypass the restriction through shell or storage. A saved snapshot proves only its recorded state, not current scheduler configuration. For an application systemd worker, inspect both system and user units and trace each ExecStart to the actual job selector; a completed job-specific timer does not prove reusable new-job dispatch. Before enabling a new unit, run a harmless read-only dependency probe as a transient service with its intended user, working directory, environment loading and hardening properties; interactive success and unit syntax do not establish service-context access. Probe the actual review CLI/model path there: a binary resolved by an interactive shell may be absent from the service PATH, so pin its installed absolute executable only after verifying it in that context. For an unattended generated-poster route, also trace the actual preparer’s final QA gate: decoded scenes and renderer fit/QR checks do not create the hash-bound semantic visual-review receipt. Compare the next product’s live catalog identity and reference image by visible equipment category before calling an isolated render a product-specific pass; a published product and a representative-image disclaimer do not make a mismatched reference suitable. Confirm a supported unattended reviewer writes genuine evidence for each newly generated campaign/scene/poster binding before claiming recurring publication readiness; a one-time human-inspected receipt only validates those exact bytes. A mismatched reference or wrong-category poster is a fail-closed content blocker, not a reason to reprompt identical rejected bytes or bypass the gate; report the next scheduled run as at risk until an accurate source and fresh exact review pass. Do not reuse an earlier receipt for the next date. For a next-day reference-workflow generated-poster preflight after an earlier semantic FAIL, compare the live series cursor and date assignment with a temporary SQLite backup of the ledger and current read-only catalog/image hash; reserve only in that copy at the next UAE date and replay it to check one product/template advance. Trace the date-specific request through Sheets job allocation and the reviewer’s actual per-job attempt/receipt path: a fresh date must not inherit an old job’s latch, but a same-request retry must retain its failed job and never mint another ID to seek PASS. Read back production cursor, assignment absence and old FAIL hashes afterward; projected job IDs are not reservations. Inspect the enabled timer’s next local elapse, service ExecStart, last failure and start-limit interval separately: a failed service from yesterday need not block a next-day start, but an enabled timer alone does not prove generation, a genuine new exact-artifact review, or publication. If `PrivateTmp` causes a setuid/ownership failure in an existing `sudo`-based read bridge, verify the real binary and repeat the probe without that property before narrowly removing it from the new unit. Read back the loaded service properties and timer's next local-time elapse after reload; do not run the publish-capable service to test scheduling. When activation is authorized only for new work, use a durable admission distinction created with new approvals, never stamp historical receipts to make them eligible. Test the filter in both CLI due selection and engine iteration against completed, uncertain, revoked and review-required historical jobs before activation. Newly admitted expired schedules may still need the existing no-publication expiry gate to emit MISSED; excluding them from all processing can silently lose that report. Keep legacy immediate recovery outside a scheduled-only rollout and report that limitation.
7. Report each boundary separately: code implemented, mock tested, active plugin replacement, actual inbound observed, tool delivery evidenced, and live scheduling verified. For a scoped reload audit, read the live Gateway plugin inventory for its `generation` and the target plugin’s runtime state (the abbreviated plugin tool inventory may omit these fields), then pair it with the reload result and Gateway journal. A queued replacement behind retained work is not activation: `committed:false` or a drain timeout leaves the previous generation active. Do not retry a failed reload merely because time passed; the logged retained-work count is a blocker, not proof of which work items remain or that they are safe to cancel. Reconcile the operation before another authorized attempt. Compare the committed generation with the pre-reload generation and the source digest recorded at activation; a current on-disk SHA256 alone does not identify the running bytes. Empty hook/command metadata and an active/enabled label do not prove that a natural-language hook handled a genuine WhatsApp or Telegram owner message. Record digest and inbound routing as unverified unless runtime evidence binds them explicitly. For production readiness, inspect the worker/timer entry point and use the existing read-only per-job status separately from global health: a nonzero recovery service exit can reflect accumulated unrelated warnings, while a verified job does not clear notification backlog. Do not run recover as a diagnostic because even its idle path can drain notifications. Before declaring a notification backlog or replaying an old event, join its delivery rows, attempt history and suppression record. An obsolete schedule notice can retain BLOCKED/PENDING rows while deliberately suppressed after later status delivery; preserve that history rather than treating it as an active failure or claiming the original notice was sent. Name the precise missing bridge and its required metadata if wiring remains unproven. Preserve protected state and distinguish historical evidence from fresh checks. Do not claim production readiness from an instruction-only workflow or mock end-to-end test.
