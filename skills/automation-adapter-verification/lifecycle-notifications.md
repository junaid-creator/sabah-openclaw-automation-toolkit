# Lifecycle notification repair

Use when owner alerts expose execution hashes, overstate completion, report false stalls, confuse skipped maintenance with failure, need a daily digest, or require self-chat echo verification. The main skill owns authorization, channel receipts and scheduler access scope; this branch does not authorize test sends or business operations.

1. Trace the lifecycle hook → journal → task state → outbox → every consumer → per-channel receipt. Inspect both system and user services. Multiple consumers of one outbox need shared atomic claims, not separate dedupe stores. Join watchdog status to outbox, delivery attempts and suppression before diagnosing backlog: a watchdog row can remain QUEUED after another consumer has already delivered the event. Preserve SENT/UNKNOWN receipts; never replay them to repair presentation. Bind each deterministic event ID to its first prepared payload: if a recovery stage or attempt count later changes, reuse the saved event rather than rebuilding a different payload under the same ID. Put a genuinely new update under a distinct event ID only when its delivery is authorized. Test the same event before and after a state transition with pending and delivered channel receipts; assert no rebinding, mutation or duplicate send. An outbox that rejects a changed payload is protecting idempotency, not evidence that its prior receipt should be cleared.
2. Recover names from registered automation/session metadata, not guesses from hashes. Determine the hook's exact hashing contract and map the original source identity using the same algorithm. Supported structured session listing can provide labels and parent keys even when a legacy sessions.json file no longer exists. Inspect the installed CLI/schema first; do not parse raw transcripts or bypass scheduler visibility restrictions. Keep internal identities and provenance privately, refresh mappings for new tasks, and retain an explicit unknown-purpose fallback when the hook discarded parent context. A name registry cannot recover missing provider-to-task correlation by itself. For an unknown cron source absent from the current job inventory, use authorized scheduler-history access to hash historical `cron_run_receipts.job_id` values with the same contract and compare exact start/request-run aliases and terminal status; a deleted temporary job can leave a valid execution receipt after its name has disappeared. Report the proven run and outcome, but do not infer its former purpose from timing or silence the global alert. For provider errors, inspect the installed model-call event and context schemas together: the observed event supplied runId/sessionKey while context also supplied jobId. Carry a hashed workflow source from trusted job/session identity and a nonconflicting execution identity; reject conflicting event/context keys rather than selecting whichever is present first. Test cron, subagent, direct-session, missing and conflicting context without inducing a real provider failure.
3. For false cron stalls, compare the hook's start and end execution keys with authoritative terminal scheduler receipts. A verified mismatch used the hash of started_at_ms at start and the hash of request_run_id at finish. Match the exact job identity plus either execution alias against exactly one receipt and exactly one tracked execution; never match by approximate time, task name or simply the latest run. Preserve both aliases because a request ID can already exist at start. Reconcile only terminal receipts; absent or ambiguous evidence leaves the task unresolved. A terminal scheduler receipt may close the exact task just before its lifecycle end hook is ingested: if no RUNNING row remains, compare the hook's exact source/execution against the already-terminal task and its authoritative receipt before emitting an unmatched needs-review alert. Treat a uniquely matched, consistent late end as an idempotent observation; conflicting outcomes or identities still require review. Repeated reconciliation must make no further state transition or notification. Where the exact receipt says skipped, record SKIPPED rather than the hook's generic error classification. Test wrong-job rejection, both start aliases, ambiguous matches, running receipts, terminal-receipt-before-end ordering, conflicting late ends, replay and skipped outcomes.
4. Separate execution outcome from business proof in the formatter. A terminal scheduler success establishes that execution ended, not that WordPress, Sheets, WooCommerce or platform results passed independent checks. Emit verification pending unless required readback evidence is actually supplied and validated by the workflow. Structured verification fixtures prove a rendering branch, not an installed verification adapter. A connectivity recovery notice describes connectivity only. Avoid adding verification claims from a status string, URL presence or runtime-generated prose. For existing recorded business results, use the receipt-adapter checks below rather than adding fresh business operations to the notifier.
5. Put deterministic formatting at the shared dispatcher boundary, scoped to the intended event family so all consumers agree without changing publication rendering or business operations. Format from allowlisted fields rather than forwarding raw errors, stack traces or execution references. Keep diagnostic detail in durable records. If routine-success suppression is authorized, retain those events locally and exclude failures, stalls, security events and recovery from it; keep start and terminal events distinct. Test one-channel failure and missing-route behavior independently in both directions, without weakening owner authorization or reclaiming attempted/uncertain sends. A dispatcher guard requiring both routes can defeat per-channel independence despite a sound ledger.
6. Back up source and consistent SQLite state before repair. For rollback, restore source only; restoring an old live outbox/ledger can replay messages or approved operations. Verify formatter and reconciliation with temporary state before activation. Test known/unknown names, unverified versus verified-fixture completion, routine suppression, critical bypass, duplicate events and sensitive-text removal. When live tests are explicitly authorized, send clearly labeled owner-only notices with the messaging tool, preserve raw receipts, then inspect an actual existing worker event separately. Manual test receipts do not establish automatic worker integration, handset reading or self-chat loop protection. A natural timer run with the new rendering and one confirmed attempt per channel supplies stronger integration evidence without manually draining historical work. Track source-on-disk, passing tests and running-plugin activation separately. A reload result with `committed:false` and a drain timeout means the previous generation remains active. Reconcile that operation before another mutation; use only the supported tool’s recovery path when authorized, without killing unrelated work or bypassing a denial. A wait-mode reload still running is not activation proof: require a committed generation and fresh service/hook registration evidence tied to the installed source. An enabled plugin does not prove changed code loaded; a management tool lacking reload/drain controls does not prove that no supported path exists elsewhere. Report the actual activation blocker, preserving any required safe-restart condition rather than treating session age as proof that unrelated work is idle.

## Model-free tool-owned delivery

Use when an application observer must report without inference but cannot invoke the messaging tool through its installed public runtime API. Inspect that API before assuming a generic tool-invocation method exists; do not substitute CLI, direct RPC or a channel sender. Where supported and authorized, a native headless script automation can own only the outbox drain with a finite `exec`/`message` tool cap; keep content generation/publication in the original workflow, not a second daily content scheduler. The local helper claims and persists receipts but never sends; the script invokes the actual message tool and returns its structured result to the helper. Share atomic claims with existing consumers and retire any replaced sender before enabling another. Bound calls/time, preserve each channel independently, and never reclaim uncertain sends.

A model-free dispatcher can itself generate watchdog STARTED/terminal alerts on every poll even with automation delivery set to `none`. For authorized suppression of this noise, trace the lifecycle source separately from the business outbox. Derive its exact source key using the installed hash contract and use an existing per-source notification override to mark only that dispatcher routine; do not disable the dispatcher, daily content job, global start notices or critical alerts. In the inspected watchdog, `notification-preferences.json` source overrides take precedence over the refreshed workflow registry, so editing that registry alone is not durable. Read and merge the existing preferences, then test that start/completion are suppressed while failure, quota, rate-limit and stall events remain eligible.

Inspect already-queued routine events separately: changing preferences can prevent future enqueueing without suppressing existing delivery rows. When authorized, use the notifier’s existing suppression ledger for only this source’s routine event IDs; preserve attempts, receipts and all critical/business events. A claim already in flight may still complete. Report policy readback and zero remaining eligible queued notices separately from observed quiet natural timer cycles; neither proves an in-flight send was cancelled. No test send, manual drain or new scheduler is needed to validate the policy.

Test the actual script executor with an empty/already-delivered outbox: successful zero-send runs establish model-free execution and tool discovery, not live transport delivery. Test claim → receipt persistence, restart after an ambiguous send, wrong-target receipts and independent-channel failure in temporary state. Keep actual historical delivery evidence separate from these checks. Do not send a new test message or drain historical work without the task’s authority.

## Recorded-result adapters

Use when the notification must report existing verification without rerunning the business workflow.

1. Inspect the producer and its durable receipt together. Bind the exact run/post/product, frozen plan hash and approval identity before accepting saved readback. Reuse a pure verifier against persisted snapshots when available. Keep publication and Sheets proof separate: a publication receipt does not prove the mirror; accept a canonical mirror-success event only after confirming its producer queues it following the required readbacks. A pending-reconciliation event is not that proof. Preserve stricter platform gates from the publication-recovery skill.
2. Normalize each source's timestamp contract before aggregating by local date; inspected ledgers used both epoch values and ISO timestamps. For a historical manual catch-up, inspect the dispatcher's event-date selector: if it drains only current-day keys, use one immutable notification key for the delivery day and carry the original article date separately. Do not rewrite the failed original run into a successful automatic run. Before a catch-up success notice, bind the new post ID and URL to independently read public WordPress status/content and the matching ledger/Sheets rows; a payload `public_verified` flag alone is not proof. Include the actual ID and live URL in the formatted message, then require per-channel tool message IDs and do not resend delivered or uncertain claims. Label results as recorded verification, not a new live audit. Missing, mismatched or incomplete receipts remain verification pending; do not promote runtime completion or free-form success text.
3. Exercise adapters with real saved receipts copied into temporary state and corrupted-binding/missing-check negatives. Patch subprocess and network entry points to fail during the offline audit. Passing those tests establishes local receipt interpretation without publication, product, Sheet or provider calls—not present remote state.

## Daily digests on an existing worker

Use only when a digest and its timing are authorized; a one-time chosen hour is not a standing schedule preference.

1. Reuse the current watchdog service, shared outbox and per-channel claims. Inspect and preserve existing timer triggers before adding a calendar trigger; validate its next local-time occurrence and read back active timer properties. For a fixed-offset zone, verify the conversion rather than copying a previous UTC hour. Do not add an LLM job or parallel dispatcher just to summarize durable records.
2. Use one durable event key per digest date in the requested time zone. Test duplicate generator invocations, restart and concurrent delivery through existing claims. Define the missed-run policy explicitly: the verified no-backlog implementation catches up after the due hour only within the same local date and suppresses older summaries at claim time. Queue-time dedupe alone cannot stop yesterday's pending delivery from being sent after restart. Preserve attempted/UNKNOWN receipts when expiring a summary.
3. Aggregate qualifying recorded outcomes and unresolved incidents rather than replaying individual alert bodies. Keep failures/stalls/security alerts outside digest suppression. Exclude authoritatively skipped runs from failure counts even when historical hook records called them errors. Show the actual snapshot time on a late same-day digest, not the nominal scheduled hour.
4. Test before-due silence, same-date dedupe, missed dates, expired queued deliveries, independent channel failure and verified-only result inclusion. Report calendar activation and mock delivery separately from the first real scheduled dispatch; do not run a production recovery/drain merely to demonstrate the digest.

## Customer reply result diagnosis and replay protection

Use when a customer inquiry is marked `model_no_reply`/`model_unavailable` despite apparent model output, or when regenerated output/retries could send more than one reply. This is distinct from suppressing transport echoes: an echo cache does not deduplicate a newly generated outbound answer.

Before attributing a `model_no_reply` guard error to provider availability, compare the exact inbound ID and customer session against the guard's inquiry/delivery rows, final-answer transcript (`stop`, provider/model and usage), and channel send receipts. Inspect the wrapper's return contract: an inbound handler may return `didSendReply=false` after a completed model answer, and a guard that treats any false result as `model_no_reply` mislabels the **delivery/result boundary**, not necessarily the provider. Check text and audio/media branches separately: a transcript-recovery path conditioned on `!ctx.audio` does not recover a voice turn. Count distinct customers from durable customer identity (older rows may lack it), not alert count; `needs_staff` is a handover flag, not proof staff has or has not resolved the conversation. A final answer proves inference, not customer delivery. Preserve uncertain sends and closed turns; diagnose and hand over without replaying under read-only scope.

1. Derive the stable turn key from trusted account, chat and inbound message ID. For a workflow allowing one customer response per turn, derive its reply ID from that turn plus a fixed reply-purpose tag, not answer text. Changed wording must not create a new delivery identity. If multiple replies are intentional, define explicit stable slots instead of silently applying the one-response contract.
2. Atomically inspect and reserve the durable delivery under a write transaction before transport handoff. Check both reply ID and turn identity so legacy content-derived IDs cannot bypass deduplication. Reject customer/turn binding conflicts. An already accepted delivery may suppress a retry; do not call its locally derived reply ID a genuine platform receipt unless the actual socket result was persisted and independently bound to that ID, account and recipient. An uncertain or failed handoff remains blocked for reconciliation, not blind replay. Evaluate current HUMAN/AUTO authorization at actual handoff, including queued sends.
3. For read-only live acceptance, anchor each inbound by trusted account, sender and transport message ID; join bounded session history, final-answer text/signature, inquiry and delivery rows, and structured channel logs in timestamp order. Trace **both** the generic queued final-answer sender and any later `supportTurn()` recovery via the inbound `reply()` closure. A `web-outbound` identity error plus `web-auto-reply` failure proves that particular handoff failed, not that a later recovery did not send. An earlier generic send attempt may even precede the final answer; count failed attempts separately from customer-visible messages. Inspect the call sites: the generic sender may lack the stable turn/reply fields required by `durableHandoff()`, while the inbound-bound closure supplies them. The combined `!meta.id || !meta.turn || !meta.text` validation does not by itself identify which field was absent; check the actual options at the guarded call. Reactions also pass through the guard without text-reply identity and can fail independently. A `recovered_model_reply` inquiry and `accepted` row prove local handoff only: if the guard accepted a locally generated key without storing the socket result, neither that key nor `Sending message` is a platform receipt. Reconcile any customer screenshot as evidence of visibility, but distinguish a supplied screenshot from a report that one exists; attribute sender, exact content, provider message ID and acknowledgment only when independently bound. A hashed destination or two failed attempts does not prove duplicate delivery. Preserve unknown-after-send entries; no replay to fill a missing receipt. Verify HUMAN/AUTO, staff escalation and failure branches separately.
4. Exercise both the generic queued final-answer path and the inbound-bound recovery path with the installed adapter, a fake socket and temporary ledgers; a static route assertion is not an end-to-end send test. Cover missing turn/reply identity, original final-answer text, provider key versus local reply ID, an earlier pre-answer failure, subsequent recovery, and no duplicate after a real or uncertain send. Also test regenerated text, alternate legacy ID for the same turn, fresh-process replay, customer-binding conflicts, chat-separated keys, late acceptance after timeout, and queued HUMAN suppression followed by AUTO; retain fallback/late-model-output guards. Distinguish local handoff, provider acceptance and delivery acknowledgment, and migrate legacy accepted rows without creating synthetic platform IDs. Run without live AI or customer sends. Offline success does not prove installation or handset delivery.
5. Before editing a source file covered by a live integrity watcher, inspect the manifest and stop policy. A transient source/hash mismatch can stop the Gateway. If activation requires a Gateway stop/restart, do not make the Gateway-hosted turn or its child process the sole deploy/rollback controller: shutdown may drain that very run before it can edit either file. Before the one authorized interruption, require an independently owned completion/rollback path through the supported operator mechanism; otherwise stop at the activation blocker rather than consuming the restart attempt. Stage and verify the exact source/manifest hashes and an isolated rollback rehearsal first. Also inspect the independent outage monitor's *actual* planned-maintenance suppression mechanism and ensure it covers the full drain, restart and channel warm-up; a deliberate systemd stop alone did not suppress outage/recovery alerts in the observed activation. If suppression is not available within the authorized scope, disclose the expected alerts rather than changing monitor policy implicitly. After any interrupted or ambiguous stop, check the supervisor's terminal receipt, both live hashes, process start time, integrity precheck, watcher state and channel listener before considering another action. If the watcher acts, correct and validate the manifest against the actual source and reconcile the queued service start. Do not force another restart or treat a matching on-disk hash or a later healthy Gateway start as activation of unchanged bytes; no new inbound turn means live customer delivery remains unverified.

## Bounded self-chat echo verification

1. Inspect the installed sender's accepted-message registration and inbound normalizer together. Verify the cache key's account, recipient/JID and message ID, any alternate-JID handling, and that a matching fromMe echo is dropped before customer/agent dispatch. Inspect late-accepted-send registration as well as the immediate-success path. Record cache expiry and restart limits; an in-memory echo guard is not indefinite durable deduplication.
2. Where the installed guard is not exported, a bounded source-extraction harness can execute its actual cache/normalizer code with mocked dependencies. Test repeated echoes, alternate JIDs, account separation, missing receipts and legitimate owner input. Record which installed code was exercised; mocks do not prove every live transport path or permission rule.
3. If owner test sends are authorized, capture a complete scoped customer-session metadata baseline, send one clearly labeled notice through the messaging tool, preserve its raw receipt, and compare the same scope afterward. No new/updated sessions supports a bounded no-loop observation, not exhaustive protection after expiry/restart. Do not alter customer routing to make the test pass. A fresh settled send can contradict a stale channel-health warning; report the receipt's actual scope without claiming handset reading.

## Delivery-state and service-exit regressions

For notification-state regressions, read delivery initialization, claim and result-recording together before classifying a state as terminal. In the reference-workflow notification worker, a zero-attempt BLOCKED route can return to PENDING when an authorized destination becomes available; a BLOCKED attempted send must remain untouched. Build fixtures with realistic attempt counts and receipts rather than weakening assertions to fit a state label. Verify route restoration, exclusive claims, retry deadlines, bounded exhaustion, stale-result rejection and preservation of attempted/uncertain receipts.

For systemd recovery exit repairs, separate execution outcome from accumulated business health. A completed empty poll can exit zero while retaining DEGRADED and historical warnings in its structured report; this exception must not silence new delivery failures, heartbeat/storage exceptions or unsafe/nonempty degraded results. Test the actual execute/main path with temporary state and mocked external effects, plus the negative cases—not only an exit-code helper. Do not run live recover merely to check its exit: even an empty publication poll may drain historical notifications.

Completion: scoped source changes, metadata coverage and unresolved mappings, exact scheduler correlation evidence, passing negative/replay tests, separate owner-tool and automatic-worker delivery evidence, preserved business scope, verified authorized scheduler deltas, and remaining activation, external-verification or echo-test limits. Claim zero additional AI formatting cost only when the formatter and metadata path make no model calls; this does not establish that the underlying automation itself is model-free.
