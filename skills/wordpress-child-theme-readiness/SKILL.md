# WordPress child-theme readiness

Use for a requested pre-activation audit or authorized switch from an existing parent theme to its official child. A read-only audit does not authorize installation, activation, cache purge, checkout transactions or scheduler changes. For a separate cart/checkout behavior defect, use [WooCommerce cart and checkout diagnosis](../woocommerce-cart-checkout-diagnosis/SKILL.md); for duplicate descriptions, use [duplicate-description diagnosis](../woocommerce-product-content-seo/duplicate-description-diagnosis.md).

1. Inventory the **live** active stylesheet/template, theme and plugin versions, PHP/runtime version and installed child directories using authenticated WordPress read APIs when possible. File presence alone does not establish activation. Obtain the proposed child from the actual vendor source; check its Template slug, style dependency and compatibility claims against the installed parent. When checking parent customization, compare installed files to the exact official version package by content hash, including missing and extra files; matching files establish absence of direct file edits, not absence of database customizations.
2. Locate theme-scoped and builder-owned state separately: menu location assignments, Customizer/Additional CSS, widgets, logo, header/footer/theme-builder display conditions, page templates, global kit styles, snippets and SEO-output switches. A child retains parent code but changes the active stylesheet slug, so theme mods and menu locations may not follow automatically. Verify each important setting after a staging switch instead of assuming transfer. A theme option that removes a parent wp_head callback can persist if the parent code still loads; verify actual fresh rendered output, including description-tag count/value, rather than editing SEO copy to mask a duplicate.
3. Map commerce dependencies without conflating installed with active: WooCommerce and gateway plugin status, product/archive builder templates, cart and checkout page IDs/content, cache exclusions and overrides. A public empty-cart checkout response cannot establish payment-gateway visibility or transaction success. For acceptance on staging, use the cart/checkout skill’s fresh same-session non-paying test and mobile checks; never place an order merely to prove theme readiness.
4. Verify backup identity and scope. For a ServMask .wpress archive, use the installed archive format to inspect entry headers, expected EOF position and stored archive CRC, confirm the root package identifies the pre-switch stylesheet/template, and check that separate database and needed content entries exist. Do not print database contents or credentials. A matching CRC and plausible entries establish archive integrity, **not** a working restore. Inspect the installed plugin’s restore/import capability and effective size limit through its read-only capabilities endpoint where available; a free importer may expose a 100 MB limit despite a much larger intact archive and require an absent extension for one-click Restore. For a manual ServMask staging restore, check the root package manifest as well as the SQL: the observed SQL imported tables under `SERVMASK_PREFIX_` and empty `stylesheet`, `template` and `active_plugins` options. In an isolated database only, replace the placeholder prefix (including relevant option/meta keys), apply the package’s recorded theme/plugin manifest, and use serialization-aware URL replacement before accepting a rendered site. Never point the staging config at production credentials; block mail, cron, outbound requests and indexing. Require a rehearsed restore on isolated staging or another independently tested rollback path before production activation. Keep a quick authenticated parent-reactivation route distinct from a full file/database restore, and verify that the operator performing the production switch has working site-owner recovery access if WordPress/REST stops booting; a successful staging restore under another Unix user does not establish this.
5. Inspect scheduled jobs and messaging accounts read-only when they are part of the requested safety scope. Distinguish external automation independence from WordPress front-end behavior: an enabled schedule or connected channel does not prove that its site read/write or notifications will still work after a theme change. Do not alter unrelated jobs to make a theme audit pass.
6. If the change is separately authorized, capture exact pre-switch settings and working pages, activate only in staging first, and compare desktop/mobile header, menu, footer, shop/product, cart/checkout, SEO tags and relevant automated readback. Check the child’s rendered Additional CSS and custom-logo mod explicitly: the observed switch copied menu locations but omitted those parent-scoped values. Migrate only verified values on staging first, preserve the parent mods, then rehearse parent reactivation and confirm its CSS/logo/menu return. If production activation is later authorized and recovery access is operable, apply the same scoped values there and verify public rendering before calling the switch complete. For an API-only production path, test the same authenticated ZIP-upload and theme-activation/parent-rollback routes on staging and verify installed file hashes; a route returning 404 while the child is absent is not an activation test. Recheck template conditions, theme-mod assignments and cache behavior. Only propose production activation after restore, staging, and production recovery-access gates are evidenced; preserve the parent for quick rollback. Report PASS, UNVERIFIED and BLOCKED separately, with the precise untested boundary. Do not claim production readiness from source compatibility, matching parent hashes or an intact backup alone.

Completion: live parent/child inventory, official source match, customization map, commerce/SEO dependencies, archive integrity versus tested restore, automation scope if requested, and an explicit activation decision with remaining gates.
