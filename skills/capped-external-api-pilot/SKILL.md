# Capped external-API pilot

## Portable installation boundary

Read [README.md](README.md) before executing this procedure. The authored
reference workflow below describes diagnostic evidence and safety gates.
Reference script names, table names, job prefixes and state paths are schema
examples, NOT commands shipped or activated by installing this skill. Map them
to the configured deployment first. Missing adapters are blockers; do not invent
commands or bypass authorization. This package is a procedural skill, not the
complete underlying engine.


Use for an authorized paid API/Actor trial or proposed recurring data-source integration. A pilot spend ceiling, time or data source is scoped to that request; it is not standing permission to run again or schedule. For owner-command and messaging receipt wiring use [automation adapter verification](../automation-adapter-verification/SKILL.md).

1. Inspect current Actor/account identity, billing cycle, used/remaining allowance, account limit and existing runs/tasks/schedules through authorized read-only routes; a scoped Actor token may not have account-billing access. Distinguish a plan's monthly ceiling from a lower user-defined budget. Confirm the existing local job's source, scheduler, lock, writer and notification path before adding anything; a name or historical snapshot is not live configuration. Do not replace a successful free source solely to use a connected paid account.
   Before using account run history as a paid-start admission gate, verify the current list endpoint’s pagination contract; a recent fixed-size window is not a complete active-run check. For Apify’s documented Actor-runs endpoint, bounded ascending `limit`/`offset` pagination was implemented and mock-tested: require integer total/offset/count/limit, expected ordering, matching counts and unique run IDs across pages. Fail closed on missing/malformed metadata, changing totals, premature empty pages or an exceeded reviewed bound. Admit only known terminal statuses; READY, RUNNING, TIMING-OUT, ABORTING and unknown states block. Recheck the first page’s total and ordered ID/status pairs before admission, rejecting drift. Keep the page/row ceiling explicit rather than claiming unbounded history coverage. Test histories larger than one page, empty history, duplicates, metadata errors, active runs on later pages and head changes; exercise the full authorized start preflight and assert zero paid POSTs and no start reservation when blocked. These tests prove local admission behavior, not live account completeness. Pagination and a local lock cannot atomically exclude another client starting after the final read; retain independent billing/cap checks and disclose that race.
2. Use the protected credential only through its supported destination-bound Gateway egress route. A masked store entry is inert for subprocesses while the egress proxy is disabled; enabling or restarting the Gateway is a separate system-management action. Gateway-hosted exec receives an opaque sentinel, not the plaintext token; native shell, sandbox, remote node and a user crontab do not inherit that grant. Never copy the sentinel/token to a runtime file, command literal, URL, log or report. Check only variable presence, then make a read-only authenticated request without printing credentials. Gateway exec captures its store snapshot at the first call in a run: after storing or changing a secret, verify from a fresh run, not another command in the old one. Verify the exact Actor and run-history access with a read-only request; a present sentinel is not valid authentication. A restricted Actor token can return HTTP 200 for those resources while `users/me` and monthly usage return 403. Classify this as unavailable account reporting, not failed Actor authentication or permission to spend. Obtain independent account-level evidence for the plan/no-overage hard stop **and** current-cycle balance; check the reserve before any start. Keep policy proof and credit proof separately timestamped: a longer, explicitly bounded policy-verification period does not extend a shorter credit snapshot. Credit evidence must belong to the active billing cycle, and a new cycle requires new balance evidence. When the provider’s account limits/usage endpoint excludes scoped tokens, do not treat Actor/run GET success as billing access, reuse an expired snapshot, or broaden the production token merely to make unattended refresh work. Check whether a genuinely read-only authorized account route exists; otherwise request fresh owner account evidence before later paid runs and fail closed when absent. A screenshot proves the values and controls only at its capture time. If current safeguards cannot be verified, fail closed without adding account scopes or fabricating a billing receipt. On a failed scheduled run, inspect the scheduler wrapper, underlying stderr if available, and durable ledger; reproduce only read-only Actor and account requests as their scopes permit. A later 401 may be current authentication failure; a 403 on account billing while Actor calls succeed is a reporting-scope blocker, neither necessarily the original run's cause. No new local run ID is evidence only about the local ledger, not remote absence or zero charge. Preserve the existing trigger unless pausing it is authorized; report its next run as at risk. Credential replacement is a separate authorized action through masked, destination-bound entry, never a plaintext workaround. After replacement, verify Actor access in a fresh Gateway execution context and reconcile remote run history and independently accessible account usage before any paid retry or re-enable. Keep authentication, schedule cadence and paid-run authority separate.
3. Inspect the selected Actor's live pricing model, per-event or per-result price, minimum start charge and input schema; compare with prior run receipts when available. If a versioned `input-schema` endpoint returns 404, read the current default build's `inputSchema` and parse it before constructing the input; a missing endpoint does not imply an Actor lacks a schema. A task's input-side max-cost field is not proof of a platform cap. For a standard pay-per-event Actor, set the API's `maxTotalChargeUsd` run option explicitly and confirm the returned run says the user set it and that the value is within the authorized limit. Bound result count, memory and timeout as secondary controls; account-wide free credit is not a per-run cap. Do not use a generic runner that cannot pass and verify the necessary cost option. Reconcile by run ID before any retry: a timeout or missing dataset is not permission to start another paid run. See the provider's current pricing and cap documentation for the exact API contract.
4. Verify the unattended execution path separately from interactive auth. A headless agent turn may lack an interactive-only `gateway_exec` tool even when its stored tool policy names it. A model-free script automation can use the Gateway `exec` tool and protected egress; test a read-only exact-Actor GET with a finite tool cap, record its actual status/exit/output, then remove the temporary probe. A scheduler's `ok` alone is insufficient if its script ignores a failed subprocess; inspect persisted state and assert the expected Actor identity and budget result. If a technical no-POST guard exists, exercise the production entry point with it before activation and confirm the ledger/Sheet remain unchanged. Normalize independently sourced billing-cycle timestamps to the ledger’s canonical key before counting spent runs or selecting an unused search (e.g. `Z` and `.000Z` may denote the same cycle); verify the dry-run selects the next search rather than replaying a completed one. Test the exact capped start, unknown-start latch and replay behavior using isolated mocks. A mocked start is not a live cap confirmation. Keep a failure alert separate from scheduler execution status: owner-only tool/provider acceptance with a message ID is not recipient-delivery proof, and a Python-owned alert cannot report a wrapper failure before Python starts. For an authorized recurring job, use a read-only observer independent of the paid entry point to warn before credit/policy evidence expires and reconcile the exact scheduled execution after its expected time. Check scheduler history **and** durable run/Sheet/notification receipts; record COMPLETE, intentional SKIPPED, missed, failed or incomplete separately. An observer success without a business receipt is not a successful paid run. Deduplicate alerts per issue and period without replaying uncertain delivery; simulate expiry, cycle rollover, insufficient reserve, missed execution, Actor failure, Sheet failure and notification failure without a billable POST. The observer itself is not a billing refresh or a second paid schedule. Do not substitute a raw user crontab for a proven protected-credential path. Inspect and merge existing schedules before activating an authorized recurring job; preserve distinct existing triggers.
5. Once the capped run is terminal, read its charged-event counts, actual charge, dataset count and records. Apply the existing qualification and deduplication criteria to the actual rows; a name regex match or row count does not make a reachable buyer. Calculate usable new leads and cost per usable lead; report zero/undefined honestly. Keep source attribution/licensing and distinguish missing contact, adjacent suppliers, consultants, site facilities and unverified buying intent. Before an authorized Sheet write, inspect whether its helper rewrites whole tabs. For append-only lead intake, read the existing IDs/schema, append only missing rows to the intended tabs, read back each, and checkpoint qualified rows so a partial-tab write can resume without re-running the Actor or overwriting review fields. Mock an interruption between tabs and verify no duplicate append on replay; a local lock does not prevent external Sheet edits. Write to a production Sheet or enable a schedule only if the request authorizes it **and** the measured usefulness and budget controls pass; otherwise preserve the original workflow and report the blocker. Record run ID, cap, actual charge and dataset ID in a receipt without secrets; verify current balance afterward through an authorized reporting route or label it unverified.

Completion for an authorized pilot: verified Actor identity, current account safeguards (via the token or an independent authorized route), enforced run cap, one reconciled run receipt, usable-lead quality/cost, independently verified unattended credential path if scheduling is requested, and explicit schedule/Sheet status. If account reporting is denied or otherwise unavailable, close the diagnosis with the scoped HTTP result, exact Actor/run evidence, local ledger/Sheet state, disabled or unchanged trigger and next-run risk; leave current account balance and any unobserved remote outcome unverified. A dated authenticated screenshot explicitly showing the current Free-plan allowance, account limit and no-overage pause can support a time-bounded guard when the scoped token cannot read billing; it is not a perpetual balance feed. Reactivate an existing authorized schedule only after its protected preflight and charge-blocked entry-point check pass, read back the next run without catch-up, and call it awaiting first live acceptance until real Actor, Sheet and notification receipts arrive. Separate API authentication, scheduler execution and business result; none implies the next.
